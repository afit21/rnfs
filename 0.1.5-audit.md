# rnfs 0.1.5 security audit

**Date:** 2026-10-17. **Code:** `main` at `5bd3075`, which is v0.1.5 plus the API proof and connection commits.
**Scope:** everything under `rnfs/`, the NomadNet companion pages, `examples/`, and the install, packaging and
release pipeline.

## Summary

There are no Critical or High findings.

- **Medium (7):** two are remotely reachable (CONT-1 needs a deny-list setting, DHT-1 does not). One leads to
  local code execution if the rnfs dir is ever loose (API-1). Two are local filesystem or provenance issues
  (CONT-2, FEAT-5), one is a CI cache-poisoning path (SUP-1), and one is a CPU-cost asymmetry on the server
  (NET-1).
- **Low:** 13 findings. **Info:** 15.
- **Earlier fixes still hold.** The H1, M1–M4, L1–L17, N1, NEW-1 to NEW-8, I2 and R1/R2 regression tests in
  `tests/security/` cover fixes that held up under re-testing. Wherever a residual issue was found (L12-R, L6,
  I2-R1), it is listed below.

## Medium

### CONT-1 (Medium): a 128 KB DAG makes the file-hash deny check hash up to 2^56 bytes

- **Where:**
  - [node.py:799](rnfs/node.py#L799) `_check_file` hashes the whole file, through `walker.read_range`, before
    anything is sent.
  - `read_range` has no output budget. Repeated subtrees are read again each time they appear, and
    `SmallLeaves` exempts large leaves from the limit that would otherwise apply.
- **Reached from:**
  - `Node._read`: `cat`, gateway GET, and gateway type sniffing at `gateway.py:605`;
  - `node_content.export_stream`: the gateway's `?format=archive`;
  - `import_archive`'s check (`node.py:1616`).
- **Precondition:** the deny list has at least one `sha256:` entry, locally or from a subscribed `deny_lists`
  source ([node.py:803](rnfs/node.py#L803)).
- **Attack:**
  1. The attacker publishes 6 blocks (about 128 KB): one 64 KiB chunk, then five file nodes. Each node lists
     the node below it 256 times, so the root declares 2^56 bytes.
  2. The victim makes a 1-byte Range GET through the gateway, or runs `cat`, `?format=archive`, or
     `rnfs import` of the 128 KB archive. A web page or rnfs page the victim opens can fire the gateway
     request, since the gateway listens on 127.0.0.1.
  - `check_disk` only runs while the DAG is incomplete. The attacker can complete it first by requesting each
    block with `?format=raw`, which never hashes DAG nodes. A declared size below the victim's free space
    skips that step entirely.
- **Impact:**
  - Each request pins a core: about a year of hashing at 1.7 GB/s.
  - Each request also holds one of the 32 `max_connections` slots, and keeps hashing after the client
    disconnects. A handful of requests exhaust the gateway and API.
  - `cat` and `import` hang. `get` is safe, because `_check_free_space` bounds it first.
- **Verified:** re-run. A 1-byte gateway read hashed 1 GiB in 0.6 s before the PoC stopped it, and importing
  the 128 KB archive did the same.
- **Fix:**
  - Cap the bytes hashed for the deny check, at `max_download_size` or a new `deny_hash_max_bytes`. Refuse
    files over the cap by policy.
  - Or refuse files whose declared size is more than K times the bytes of their distinct blocks.
  - Give `read_range` an optional output-byte budget either way.

### DHT-1 (Medium): a stalled lookup leaves keeper `/name` queries 1 s

- **Where:**
  - [keepers.py:809](rnfs/features/keepers.py#L809): `deadline = time.monotonic() + max(1.0, lookup.remaining())`.
  - `enough()` (around `:745`).
  - `dht/lookup.py` `_iterate`, which has no bound on rounds or progress: only `lookup_timeout` (600 s) ends
    it.
- **Attacker:** a few hundred announced Sybil server IDs ground close to `name_key(name)`. Grinding runs at
  about 31k IDs/s per core, so 17 matching bits took 5 s. Each Sybil answers `/find` slowly, returning fresh
  Sybil IDs that are closer to the key, so the beta closest nodes never all finish answering.
- **Impact:**
  - For a typical name with fewer than 3 × alpha keepers, `enough()` never fires. The provider search uses
    the whole `lookup_timeout`, and the `/name` queries then get 1 s.
  - A link to a real keeper needs seconds to establish, so its answer is dropped.
  - As a result, every keeper-fallback resolve, follow check and `retry_missing` for that name fails. Each one
    also blocks its caller for more than 10 minutes.
  - That is exactly the case keepers exist for: the owner is offline.
  - A slow radio mesh can starve the queries the same way with no attacker.
- **Verified:** re-run. Without Sybils, sequence 2 resolved in 1.5 s. With 491 Sybils stalling the lookup it
  resolved nothing after 6.0 s, even though the keeper was asked.
- **Fix (wire-compatible):**
  - Give the `/name` queries their own time budget: at least `path_timeout`, plus link setup, plus the RNS
    request timeout.
  - Query candidates as they are found, or stop the provider search once candidates exist and part of the
    budget has passed.
  - In `Lookup`, end after N rounds without the beta-closest set changing, or cap the number of queries.

### API-1 (Medium): POSIX never checks `rnfs.toml` or existing subdirectories

- **Where:**
  - [config.py:274-282](rnfs/config.py#L274-L282): `winacl.secure_settings` returns `None` off Windows
    ([winacl.py:363-365](rnfs/winacl.py#L363-L365)).
  - `node.py:138-139`: `makedirs(..., exist_ok=True)`, with no owner or mode check on subdirectories.
  - `rnfs.toml` is read at `cli.py:186`, before `lock_rnfs_dir` tightens the root at `:200`.
- **What the spec requires:** §11 says `rnfs.toml` MUST be checked through its open handle: refused if
  another user owns it, made private if others can access it. Windows does this; POSIX does nothing.
  Subdirectories that already exist (`state/`, `names/`, `storage/`, `blocks/`) are never checked or
  tightened.
- **Attacker:** a local user who could write in the rnfs dir at some point before the daemon tightened it,
  for example a group-writable or shared `--dir`. Tightening the root to 0700 later does not remove their
  access to subdirectories: they can keep a directory fd open, or keep subdirectories they created.
- **Impact:**
  - A planted `rnfs.toml` can set `reticulum_dir` to a config with a `PipeInterface` `command=`. That is
    code execution as the victim.
  - Write access to `blocks/` lets them plant blocks: stored raw blocks are trusted by length
    (`fetcher._check_stored`).
  - The identity file (I2-R1) already got this protection, from the same starting condition.
- **Verified:** re-run. A 0666 `rnfs.toml` loads with no warning. After `lock_rnfs_dir` the root is 0700 but
  its subdirectories stay 0777. That ownership isn't checked comes from reading the code; changing a file's
  owner needs root.
- **Fix:**
  - On POSIX, open `rnfs.toml` with `O_NOFOLLOW` and `fstat` it. Refuse if `st_uid != geteuid()`, and
    `fchmod` it to 0600 with a warning if group or other bits are set.
  - In `_make_private_dirs`, `lstat` each subdirectory. Refuse a symlink, a non-directory or a foreign owner,
    and `chmod` loose ones to 0700.

### FEAT-5 (Medium): a name link quietly falls back to the sender's CID

- **Where:** `features/lxmf.py` `_resolve` (around `:1300-1320`) and `_print_links` (around `:1683`).
- **Attacker:** any LXMF sender, strangers included.
- **Attack:**
  - The rnfs field of the message carries both `name` and `cid`.
  - `rnfs inbox` shows only `rnfs:name/<name>/...`, never the CID.
  - When the user runs `rnfs inbox get N` while the name can't be resolved (owner offline, no keeper
    reachable: common on a mesh), `_resolve` silently uses the sender's CID. The only trace is a NOTICE in the
    daemon log.
- **Impact:** a stranger can pose as a well-known name, such as a project's release name. The user saves the
  attacker's file under the shown file name, believing it came from that name. The content still matches its
  CID, but its origin is misrepresented. Auto-fetch has the same fallback, though only for trusted senders.
- **Verified:** re-run. The CLI never shows the CID, and `inbox get` writes `installer.sh` with the attacker's
  content.
- **Fix:**
  - When the user runs `inbox get` and the name can't be resolved, fail, unless they pass an explicit
    `--use-sent-cid`.
  - Show the sent CID next to name links in `rnfs inbox`.
  - Report any fallback as a warning in the command's result.

### CONT-2 (Medium on Windows, Low on POSIX): write-out follows a swapped directory

- **Where:** `content/walker.py` `write_out` (around `:490-527`).
  - It runs `os.mkdir(path)`, then writes that directory's children later, by path, after all its siblings.
  - Nothing checks that the directory is still the one it created.
- **Attacker:** a local user who can rename entries inside the output tree.
  - On POSIX, a group member, if the victim uses umask 002 in a shared setgid directory.
  - On Windows, any Authenticated User, if the output is under a folder whose inherited ACL grants Modify.
    That is the default for folders created directly under `C:\`.
- **Impact:**
  - Between the mkdir and the child writes, the attacker swaps `partial/sub` for a symlink or junction.
  - `get` then creates the DAG's files, executable bit included, in a directory the attacker chooses
    (`~/.config/autostart`, the Startup folder). That can lead to code execution as the victim.
  - `open(..., "xb")` stops existing files being overwritten, but not new files being created.
- **Verified:** re-run. The PoC does the swap deterministically, and `evil.desktop` is written into the
  attacker's directory.
- **Fix:**
  - Create the `.rnfs-get-*.partial` root as 0700 (on Windows, with `winacl.make_private_dir`), and relax its
    mode just before `rename_new`.
  - Where the platform allows, create entries relative to the parent's fd: `mkdir(dir_fd=)` and
    `os.open(O_CREAT|O_EXCL|O_NOFOLLOW, dir_fd=)`. Reopen each new directory with `O_DIRECTORY|O_NOFOLLOW`
    and check its dev/ino.

### SUP-1 (Medium): the release Flatpak build restores a poisonable Actions cache

- **Where:** [release.yml:159-165](.github/workflows/release.yml#L159-L165). The flatpak-builder action at the
  pinned SHA (v6) defaults to `cache: true`.
  - It restores the exact key `flatpak-builder-<sha>-x86_64`, and otherwise falls back to the prefix
    `flatpak-builder-x86_64`.
  - A tag run can restore caches saved from the default branch.
- **Attacker:** code execution in any default-branch workflow run, even a `contents: read` job. The runner
  token can write the cache whatever `permissions:` says. A `workflow_dispatch` of `release.yml` on main also
  works.
- **Impact:**
  - Poisoned cached modules or ccache output end up in `rnfs.flatpak`.
  - The bundle is then checksummed and attested as genuine.
  - The `release` environment gate reviews only the publish step, not what was built.
- **Fix:** set `cache: false` on the step, or `restore-cache: false` and `save-cache: false`.

### NET-1 (Medium): cancelling a `/blocks` response after its first parts gets no cooldown

- **Where:** `network/server.py:1207-1228` (`_concluded` / `_sent_any`).
- **What happens:** the L17 cooldown applies only when a Resource is rejected with nothing sent. A requester
  that cancels after any part arrives can ask again at once.
- **Impact:** each round makes the node read and SHA-256 every block, pack them, then build and encrypt a
  whole Resource with its hashmap:
  - about 1 MiB per response once the link has a rate estimate;
  - about 192 KiB before it has one.
  - The requester only has to receive the first window of parts. The cost asymmetry is CPU, not bandwidth.
- **Background:** `test_l17_rejected_responses.py` deliberately treats a rejection mid-transfer as honest, so
  this is a design residual, but its cost hadn't been weighed.
- **Verified:** PoC on the server test harness.
  - A reject with nothing sent gets a cooldown. A cancel after progress, or a reject after progress, gets none,
    and the same link takes a new `/blocks` slot at once.
  - A 1 MiB response costs the responder about 0.5 ms of build CPU per round (re-hash and pack), against about
    0.003 ms for the requester: roughly 185×.
  - RNS's Resource encryption and hashmap build add responder-only cost on top, which wasn't measured live.
  - One link is limited by round trips (one `/blocks` in flight per link), so it forces only a few to tens of
    rounds a second. Scaling the attack takes many links, up to `max_incoming_links` = 128.
  - Rated Medium for the asymmetry. The absolute cost per link is modest.
- **Fix:**
  - Treat a response the requester cancelled after receiving only a small fraction (under one window, or under
    5%) as no progress. Apply a short, growing cooldown per link and per identity.
  - Or cap how many never-completed responses a link may cause per minute.

## Low

### DHT-2 (Low): a replayed announce inherits the newest emission time
- **Where:** `names.py:888-894` (`_absorb_recalled` → `_announce_heard`).
- **Mechanism:**
  - RNS's `Identity.remember` overwrites the stored app_data for any validly signed replay.
  - The path table keeps the newer announce's random blob, and `emitted_time` reads that blob.
  - So an old record is paired with the new emission time, and looks fresh.
- **Attacker:** a neighbour holding old announces, against a resolver with no floor for the name. For
  example, a first resolve, or a name that was only heard and then pushed out.
- **Impact:**
  - A CLI or API resolve returns and persists the old sequence with age 0, and keepers that hold the newer
    record are not asked.
  - The same applies to deny-list and contacts resolves, and to the `max_age` fast path.
  - The spec's statement that a first resolution can't detect a replay is not true here: RNS already holds
    proof of a newer emission.
- **Verified:** re-run (returns sequence 3; no keepers queried).
- **Fix (wire-compatible):** get the remembered announce's own emission time from its packet hash, as
  `keepers` already does with `known_destinations[name][1]` → `Transport.get_cached_packet`. If it is older
  than the path's, treat the record as a replay: use its own emission time as heard, and ask keepers.

### DHT-3 (Low): a followed name's owner can fill the follower's disk
- **Where:** `features/follow.py:316` (`fetcher.open(target, pinned=True)`). The default
  `max_download_size` is None, and pinned fetches never stop at, or evict for, `max_storage`.
- **Impact:**
  - A followed name can pin content of any size, up to the disk reserve.
  - During a target swap it briefly holds about twice that.
  - Unlike LXMF auto-fetch, there is no per-source quota.
- **Verified:** re-run (`max_storage` 64 KiB, 4.2 MB pinned).
- **Fix:** add a per-follow size cap (for example `follow_max_size`, defaulting to a fraction of
  `max_storage`), or count follow pins against `max_storage`.

### FEAT-1 (Low): one auto-fetch sender can push out another's pinned messages
- **Where:** `features/lxmf.py:599-614` (`MessageLog.add`), `_fetch_and_pin` (around `:1505`), and `received`
  (`per_from=None` for auto senders).
- **Mechanism:**
  - Re-linking a CID the sender already pins records "pinned" without using quota, and those records are
    protected.
  - Auto senders have no per-sender cap, so about 500 such messages fill the inbox.
  - After that, each new message evicts the oldest record overall, including another sender's pinned message,
    and `_release` unpins it.
- **Impact:** this breaks the spec's threat-table promise (spec line 1001, "auto-fetched pins never pushed out
  by others' messages").
- **Verified:** re-run. The attacker used 47 bytes of quota; the victim's message and its `lxmf:` pin are gone.
- **Fix:**
  - When every record is protected, drop the incoming sender's own oldest record, or refuse the message.
  - Cap auto senders per sender as well (a share of `INBOX_LIMIT`).
  - Don't count repeated records of the same CID as protecting.

### FEAT-4 (Low): queued auto-fetches still run after the sender is removed
- **Where:** `features/lxmf.py` `_requeue_auto_fetches` (around `:1404`) and `auto_fetch` (around `:1445`).
  Neither checks that the sender is still in `lxmf_auto_fetch_from`.
- **Impact:** after a restart, up to 64 of a removed sender's queued links are fetched and pinned anyway.
  `_load_remote_pins` already filters remote pins against the current list; this path doesn't.
- **Verified:** re-run (state "pinned", `lxmf:` pin held).
- **Fix:** skip, and mark "refused", any queued record whose sender is no longer listed. Check both when
  re-queuing and inside `auto_fetch()`.

### FEAT-3 (Low): many identities starve all strangers' messages
- **Where:** `features/lxmf.py:1263` (`_untrusted_token`).
- **Mechanism:** the L12-R allowance limits each identity, but strangers share one node-wide bucket (32 burst,
  then 1 a minute). LXMF identities cost one announce each. One message a minute, each from a fresh identity,
  keeps the bucket empty.
- **Impact:** every other stranger's message is dropped. Trusted senders are unaffected.
- **Verified:** re-run (0 of 36 strangers' messages kept over a simulated 6 hours).
- **Fix:**
  - Announce and enforce an LXMF `stamp_cost` (proof of work) for untrusted senders.
    `_announce_app_data` currently announces `None`.
  - At least, document that this design only stops a single identity.

### FEAT-2 (Low): display names can fake a trusted address in `rnfs inbox`
- **Where:** `features/lxmf.py` `_run_inbox` (around `:1695`).
- **Mechanism:** the sender's display name comes from their own announce. It is printed first, unmarked, and
  up to 64 printable characters fit `alice <TRUSTED_HEX>` plus padding. The real address is pushed off to the
  right. Contact nicks and trust are never shown.
- **Verified:** re-run:
  ```
  #7  2023-11-15 08:43  alice <51515151515151515151515151515151>                         <deaddeaddeaddeaddeaddeaddeaddead>  direct
  ```
- **Fix:** print the address first and the display name quoted after it. Show the contact nick for contacts,
  and mark every other sender as untrusted.

### API-2 (Low): before the proof, a fake listener chooses the client's error
- **Where:** `apiclient.py:336`. `verify_daemon` calls `_send`, which turns the status into an exception
  through `error_for` (`:296-302`) before the proof is compared.
- **Impact:**
  - While the daemon is down, a process listening on its port can answer 451, 404 or 507 with any message.
  - `rnfs.Client` then raises `Denied`, `NotFound` or `StorageFull` carrying the attacker's text, instead of
    `AuthFailed`. Apps act on that result.
  - The token is never sent.
  - The proof exchange also has no default timeout, so the fake listener can hang a client indefinitely.
- **Verified:** re-run.
- **Fix:** check `X-Rnfs-Proof` before mapping any status; any response without a valid proof becomes
  `AuthFailed`. Bound the proof exchange with a short timeout.

### NET-2 (Low): single-packet `/blocks` responses skip pacing
- **Where:** `network/server.py:961-984` (`single = packed <= mdu` returns the response body directly) and
  `:946` (`cap` is None without a rate estimate).
- **Impact:** single-packet responses free their slot at once and never produce a rate estimate.
  - `max_upload_rate` therefore never applies to a requester that only asks for blocks fitting one packet.
    The only per-link limit left is the 2000/s request bucket.
  - This needs a large-MTU path: TCP interfaces allow about 16 KiB, Backbone about 32 KiB.
  - `upload_budget` still charges these responses in full.
  - It matches the spec's wording ("once it has a rate estimate"), but an operator who sets `max_upload_rate`
    would not expect it.
- **Verified:** PoC on a fake link with a 32000-byte MDU and `max_upload_rate` = 1000 bit/s. 50 single-packet
  responses (1 MB in all) were served with no pacing delay, and the rate estimate stayed None. A multi-packet
  response afterwards got a 480 s wait.
- **Fix:** pace single-packet responses too, using `unmeasured_bitrate` or the interface bitrate when there is
  no estimate.

### NET-3 (Low): request packets on outgoing links are decoded before any rnfs check
- **Where:** `network/guards.py:245-264`, which guards only response-context packets.
- **Mechanism:** on links rnfs opens, the remote destination has no `max_request_size`. RNS therefore
  msgpack-decodes any request packet, up to the link MDU, and starts a thread for it before finding there is no
  handler.
- **Impact:** some memory and thread use, which any node rnfs contacts can cause.
- **Verified:** PoC. `guarded_receive` forwards a request packet on an outgoing link to RNS, while it drops an
  oversized response on the same link. The RNS 1.5.6 side (decode plus a thread for each packet, `Link.py`
  around lines 994-1006) is read from source, not run live. Since the attacker must be a node rnfs chose to link
  to, it is a modest amplifier.
- **Fix:** in `guarded_receive`, drop request-context packets on rnfs.dht links this node opened, without
  reading them. This mirrors the existing drop of responses on incoming links.

### SUP-2 (Low): `install.sh` doesn't tie the checked sdist to the requested tag
- **Where:** `install.sh:350-357` and `:534-537`.
  - `gh attestation verify` gets `--repo` and `--signer-workflow`, but no `--source-ref`.
  - The wheel loop accepts any `rnfs-*.whl`.
- **Impact:** with release-asset write access, an attacker can rename an older, genuinely attested sdist (a
  known-vulnerable version) to the new version. It passes both SHA256SUMS and the attestation check.
- **Fix:**
  - Pass `--source-ref refs/tags/$RELEASE_TAG` (and `--deny-self-hosted-runners`) where `gh` supports them.
  - Require the wheel to be named `rnfs-${RELEASE_TAG#v}-*.whl`.

### SUP-3 (Low): provenance checking is off by default
- **Where:** `install.sh:363-370`.
- **What happens:** without a logged-in `gh`, which covers most `curl | sh` users and root, the only check is
  SHA256SUMS from the same release. That only shows the download is complete. This is documented, and
  `RNFS_REQUIRE_ATTESTATION=1` makes the check required.
- **Fix:** require the check whenever `gh` is available, and say plainly in the README that `curl | sh`
  depends on who can write GitHub release assets.

### SUP-4 (Low): the `rnfs` name on PyPI is unclaimed
- **What happens:** `https://pypi.org/pypi/rnfs/json` returns 404, while README.md:322 says plain
  `pip install` works. Anyone can register `rnfs`, and a user running `pip install rnfs` would get their code.
- **Fix:** register the name, either by publishing through trusted publishing or with a placeholder that
  points to GitHub.

### SUP-5 (Low): the Flatpak sandbox is nominal
- **Where:** `packaging/flatpak/io.github.afit21.rnfs.yml:19,23` grants `--filesystem=home` and
  `--device=all`.
- **Impact:** rnfs parses untrusted network input. If the daemon is compromised, it can write `~/.bashrc` and
  escape the sandbox.
- **Fix:** narrow it to `~/.rnfs:create`, `~/.reticulum:create` and `xdg-download` (or use portals), and make
  `--device=all` opt-in.

### CONT-2 on POSIX
See [CONT-2](#cont-2-medium-on-windows-low-on-posix-write-out-follows-a-swapped-directory). On POSIX it is Low,
because the default umask keeps others out of the output tree.

## Info

|---|---|
| CONT-3 | `SharedFolder.scan` follows a symlink at `files/` (by design). If the owner points it at a directory whose parent another user can write, that user can retarget it at `~/.rnfs/storage`. The identity file would then be pinned and served, though only to someone who knows its unguessable CID. Possible fix: warn when the folder's parents aren't owner-only, or pin the folder's dev/ino. |
| CONT-4 / API-6 | A `sha256:` deny entry doesn't stop a multi-chunk file being served chunk by chunk (`?format=raw`, `/blocks`). Documented in spec §8 ("deny the CID for that"). |
| API-3 | Unauthenticated callers also get the kept-open proof connection (`api.py:753-766`). This doubles how long the accepted slot-exhaustion DoS can hold a slot (about 2 × `request_timeout`). The keep-open is otherwise bounded to exactly one more request. |
| API-4 | The fallback reconnect (`apiclient.py:324-326`) keeps the old proof-then-reconnect race for pre-0.1.5 daemons. Fall back only when `daemon_version < 0.1.5`, and drop the fallback later. |
| API-5 | A user HEAD, or a range not starting at 0, sniffs the first 512 bytes of a denied stored chunk (`gateway.py:607` → `node_content.stored_head:174`, which bypasses the deny list). Only the Content-Type leaks. A HEAD of a hash-denied file answers 200 where GET answers 451. |

| DHT-6 | The K = 10 closest IDs to any key can be ground in seconds (about 31k IDs/s per core), which makes eclipsing a key cheap. Already listed in spec §10 Limits; noted here only for the cost. Fixing it needs a design change. |
| NET-4 | A malicious provider can hold one of our `/blocks` fetches for hours: with no rate estimate the stall deadline assumes 100 bit/s, so 64 KiB takes about 4.4 h. Matches the spec; whether it matters depends on the fetcher racing other providers. |

## Checked and found sound

**Network:**
- Request parsing is strict: types, duplicate CIDs, the 55-key `/provide` cap, bool kept apart from int. RNS
  enforces the 1 KiB request limit before decoding.
- Handler exceptions are contained by `_guarded`.
- Response parsing is bounds-checked, with nothing allowed after the response.
- The Resource advertisement guard refuses request Resources, oversize transfers, multi-segment, metadata and
  compressed advertisements.
- Identity binding holds for `/provide` and LinkPool.
- Private mode is enforced on every handler.
- `/pin` is checked against the allowlist before parsing.
- `/blocks` serves only DAGs this node provides, checks the deny list first, and has no storage oracle.
- Bookkeeping maps are bounded.
- H1, M1, M2 and L17 have not regressed.

**Content:**
- CIDs: only the exact raw and rnfs-dag sha256 prefixes are accepted, the text form is canonical, and no CID
  is built from untrusted bytes.
- DAG decoding is strict, with a byte-identical re-encode check, and validates names, order, kinds and size
  overflow.
- The walker checks each block against what was expected and dedupes repeated nodes, so repeated CIDs can't
  blow up exponentially.
- Export names are sanitised for POSIX and Windows, including ADS, reserved names and trailing dots or spaces.
  Writes use O_EXCL.
- Archives cap and verify everything before use.
- The fetcher verifies blocks and drops unrequested ones.
- Sealing is encrypt-then-MAC with a constant-time HMAC check before unpadding, HKDF-separated keys, a random
  IV per segment, and tags that bind the header, index and final flag.
- The builder and shared folder use fd-relative `O_NOFOLLOW` opens with a dev/ino recheck, and skip hard
  links, so the L8 and L8-R2 fixes are complete on POSIX.
- `winacl` was reviewed but not run on Windows.

**DHT and names:**
- A name record's signature covers every field, and the destination hash is checked before the signature.
- Records are canonical msgpack.
- The rollback, floor and sequence rules hold, and far-future times are clamped.
- The L4/L4r and M3/M3r1/M3r2 fixes are complete.
- A 120-seed provider-store fuzz (`fuzz_providers.py`), with clock jumps, retain, save and reload, held every
  accounting invariant.
- Routing admission, bans and pruning hold.
- Lookup replies are trimmed, and requests for unknown IDs are budgeted.
- Private-mode membership checks hold.
- Keeper storage is bounded, and records are re-verified.

**API and gateway:**
- The token is 256 bits, compared with `compare_digest`, and checked before any body is read. Only
  `/api/status` is open, and it returns just the version.
- The challenge proof is bound to the port.
- The token file is written atomically with O_EXCL, O_NOFOLLOW and mode 0600.
- Host is matched exactly, which blocks DNS rebinding. No CORS headers anywhere.
- Every gateway response, including `http.server`'s own errors, gets `CSP: sandbox` and `nosniff`.
- `filename*` is percent-encoded, so there is no CRLF injection.
- All SQL is parametrised, and the state DB and its WAL/SHM files are 0600.
- The debug log is opened O_EXCL, mode 0600, and contains no secrets.
- Deny-list CIDs are canonical, so there is no alternate-encoding bypass, and they are checked on every path.

**Features and CLI:**
- LXMF accepts only signature-validated messages.
- Strangers can never trigger fetches or pins.
- Inbox, outbox and the hold queue are bounded (L12, L13 and L13-R complete).
- The auto-fetch quota holds.
- Jobs are re-validated when loaded.
- Contact trust is per kind.
- Every untrusted string the CLI prints goes through `printable`.
- The page scripts validate their parameters, call subprocesses with argument lists and no shell, and escape
  Micron output correctly.

**Supply chain:**
- All 52 lock pins are `==` pinned with `--hash`, matching PyPI exactly. None are yanked or carry a known CVE.
- Installs use `--require-hashes --only-binary=:all:`.
- Every Action is pinned by SHA (verified against the upstream tags), and containers by digest.
- No `pull_request_target`, and no `${{ }}` values spliced into `run:`.
- `persist-credentials: false`, and permissions are least-privilege.
- SHA256SUMS is attested.
- `install.sh` uses `-I`, `mktemp`, safe tar and zip extraction, and refuses to overwrite files it didn't
  make.
- The service files run as the user, never as root.

## Method

- **Six agents in parallel**, one per attack surface: network server; content and filesystem; DHT, names and
  keepers; local API and gateway; LXMF, features and CLI; supply chain.
- Each read the relevant parts of `specification.md` and the existing `tests/security/` regression tests
  first. The aim was to check old fixes for completeness rather than report them again, and to focus on code
  new in 0.1.5 (about 7.8k changed lines).
- PoCs ran against the real code with the test suite's fakes. pytest isn't installed in this environment, so
  they run under `unittest`.
- Every finding marked "PoC, re-run" was run again for this report.
- **Existing regression suite:** `python3 -m unittest discover -s tests/security -p "test_*.py"` ran 474 tests,
  all OK, with 35 skipped. The skips are the RNFS_E2E real-RNS cases.
- Not covered:
  - live tests over real RNS (the RNFS_E2E suites);
  - running `winacl` on Windows;
  - the GitHub repository settings: required reviewers on the `release` environment, and tag rulesets.

## Suggested fix order

1. **CONT-1, API-1, CONT-2:** small, contained changes that close a remote DoS and two paths to local code
   execution.
2. **SUP-1, SUP-4:** a one-line CI change, and claiming the PyPI name.
3. **DHT-1, FEAT-5, FEAT-1, FEAT-4:** all wire-compatible.
4. **NET-1, NET-2, NET-3, DHT-2, DHT-3:** these need small design decisions (cooldown policy, a follow quota).
5. Then the remaining Low and Info items. FEAT-3 needs a decision on LXMF stamps.
