# Make Sybils rent, not buy, storage

RNS has no single scarce resource for rnfs to attach a per-publisher cap to, so the cap should depend on a ranked set of signals. First comes the server operator's own trust list. Second is seniority the server has observed itself. Third is recurring memory-hard work, which is how strangers pay. Fourth is ingress location, used only where the server can actually see it. RNS identities are free, so any cap keyed on the identity alone grows with the number of identities. Under today's parameters, about 100 identities that waited one day can claim a whole 100k-record server. The working idea, a one-time proof-of-work stamp per identity, runs into the literature's central point: **a one-time cost limits how fast an attacker gains identities, not how many it holds**. Provider records refresh for free, so stamped allowance piles up without limit. Binding the stamp to a 7-day epoch that matches `PROVIDER_TTL` stops the pile-up. Even a recurring stamp is a price, though, not a barrier. At the roadmap's own calibration, a rented RTX 4090 buys a full server's worth of allowance in about 3 seconds with SHA-256, or about 90 seconds with scrypt. Every server honours a stamp, so that allowance applies network-wide. Stamps should therefore buy a bounded slice of the store and never be able to evict senior or trusted publishers. A publish cap only addresses storage exhaustion. Key eclipse needs about K=10 ground IDs and no storage, so it has to be fixed in lookups. All of this is local server policy plus the `/stamp` request, which is already planned as 0.2.0's one additive wire change, so nodes on 0.1.3 and later keep working.

## Free identities turn every per-identity cap into a multiplier

Douceur's result frames the problem. Without a trusted certifying authority, Sybils cannot be prevented in general, and resource tests only reduce how many identities an attacker can afford ([Mohaisen & Kim survey](https://arxiv.org/pdf/1312.6349)). For rnfs, the arithmetic is short. A server holds 100k records, newcomers get 100 each from a 10% pool, and publishers seen for a day get 1000. So **100 fresh identities fill the newcomer pool, and 100 identities that announced once and waited a day fill the entire server**. A token bucket does not change this: it slows each identity, and the attacker runs identities in parallel ([Mohaisen & Kim survey](https://arxiv.org/pdf/1312.6349)). Per-identity rate limits still have uses: catching a buggy honest publisher, and protecting CPU and LoRa airtime when keyed per link or per interface. But they bound nothing against Sybils unless the thing being rate-limited is scarce.

What deployed systems do confirms this. No open DHT we checked caps stored records per publisher at all. In IPFS, `handleAddProvider` checks only that the provider is the sender and has an address. Provider storage is bounded by datastore size and a 48h expiry ([go-libp2p-kad-dht handlers.go](https://github.com/libp2p/go-libp2p-kad-dht/blob/master/handlers.go), [amino/defaults.go](https://github.com/libp2p/go-libp2p-kad-dht/blob/master/amino/defaults.go)). HyperDHT uses a global 65,536-record LRU with a 20-minute TTL ([hyperdht index.js](https://github.com/holepunchto/hyperdht/blob/main/index.js)). libtorrent caps 2000 torrents and 500 peers per torrent ([libtorrent settings](https://www.libtorrent.org/reference-Settings.html)). Wherever Sybil resistance exists, it is keyed on something other than the keypair:

| System | How record storage is bounded | What Sybil limits key on | Works without IP or an authority? |
|---|---|---|---|
| IPFS Amino ([defaults](https://github.com/libp2p/go-libp2p-kad-dht/blob/master/amino/defaults.go)) | 48h expiry, datastore size; no per-peer count | /16 or /8 IP group in routing table (3 per table, 2 per bucket) | No |
| Mainline / libtorrent ([BEP 5](https://www.bittorrent.org/beps/bep_0005.html), [BEP 42](https://www.bittorrent.org/beps/bep_0042.html)) | Global 2000 torrents, 500 peers each | IP return-routability token, ID derived from IP (off by default), one routing entry per IP | No |
| discv5 TopDisc ([spec](https://github.com/ethereum/devp2p/blob/master/discv5/discv5-theory.md)) | 1000-ad cache, 15-min ads, one ad per advertiser per service | Waiting time rising with occupancy, service share and IP-prefix imbalance | Partly (the occupancy term needs no IP) |
| Tor HSDir ([dir-spec](https://spec.torproject.org/dir-spec/assigning-flags-vote.html)) | Not specified in the pages read | Authority-assigned flag: 96h uptime, Stable, Fast, at most 2 relays per IP | No |
| I2P floodfill ([netdb docs](https://i2p.net/en/docs/overview/network-database)) | Short lifetimes (LeaseSets 10 min); no numeric quotas published | Self-selection by 128 KB/s bandwidth; daily keyspace rotation | Yes, and weak by I2P's own account |
| HyperDHT ([persistent.js](https://github.com/holepunchto/hyperdht/blob/main/lib/persistent.js)) | Global LRU, 65,536 records, 20 min | Node ID = hash(IP:port), store token, 20–30 min ramp before storing | No |
| GNUnet R5N ([LSD0004](https://lsd.gnunet.org/lsd0004/)) | Mandatory eviction, optional quotas | Prefer the oldest working connections | Yes |
| KAD / eMule 0.49a ([Kohnen et al.](https://networking.ifip.org/2009/Website/proceedings/networking/1569170497.pdf)) | Not covered by the sources read | 1 ID per IP; 2 per /24 per bin, 10 per table; bypassed in practice | No |
| Nostr ([NIP-13](https://github.com/nostr-protocol/nips/blob/master/13.md)) | Each relay's own policy | Per-event PoW with committed difficulty; WoT relays | Yes |

The pattern is clear. Limits that hold up are keyed on **IP or subnet, a central authority, elapsed time, or bandwidth**. RNS exposes none of these at protocol level. The only mechanisms that work without IP or an authority are time gating, admission cost that rises with occupancy, per-key caps, short TTLs and proof of work. None of them stops a patient attacker. Storage exhaustion gets little attention. R5N is the only spec that names it ("may attempt to exhaust the storage capacity of honest nodes"). Everyone else turns record spam into displacement through global LRU caches and short TTLs, so honest publishers re-insert within minutes ([LSD0004](https://lsd.gnunet.org/lsd0004/)). rnfs's 7-day TTL is long next to Amino's 48h and HyperDHT's 20 minutes, so **a flood that gets into an rnfs store stays for a week**. This is why rnfs needs eviction priority rather than refusal alone. rnfs's existing 100/1000 per-publisher cap is already stricter than anything deployed. The question is not whether to cap but what to key the cap on.

## One-time stamps buy identities; recurring stamps only rent them

SybilControl states the distinction that decides the working idea. A computational cost paid before joining gives an adversary "an upper bound on the **rate** they can acquire identities", but only if "nodes are required to periodically repay this computational cost" is "the **number** of identifiers that can be maintained by the adversary" limited ([SybilControl, arXiv 1201.2657](https://arxiv.org/abs/1201.2657)). Rowaihy et al. found the same thing empirically. One attacker with 5-minute puzzles takes 10% of IDs in an 8,000-node network in 77 hours. Their fix is a cut-off window W after which "an attacker with n IDs will have to acquire n new tokens". Windows of 4h and 8h kept attackers under the 10% target ([Rowaihy et al. 2007](https://www.cse.psu.edu/~tfl12/paper/Sybil.pdf)). In rnfs a never-expiring stamp is worse than in node admission, because records refresh at no cost. An attacker minting S stamps a week holds about 52·S fully capped identities after a year. **The one-time stamp in the current roadmap therefore fails as a Sybil bound.** What it limits is accumulation speed, and patience defeats that.

The rest of the roadmap design is sound, and much of it should stay. Granting `max_records/100 × 2^(c − c0)` records makes the cost per allowed record a constant 2^c0/base hash evaluations, however the attacker splits work across identities. Splitting gains the attacker nothing, so the formula is Sybil-neutral within the stamped population. Lazy sending only on refusal, caching per publisher, and limiting checks per link are all good choices. The fix is to make the stamp expire. Put the epoch in the workblock (`context ‖ node_id ‖ epoch`), set the epoch length to the 7-day `PROVIDER_TTL`, and accept the current and previous epoch. Allowance then becomes a steady rate: stamps per week times cap per stamp. The honest cost is one stamp per publisher per week, sent once to each server, which is an 8–16 byte nonce and well under a second of airtime at 1 kbit/s. Precomputing future epochs is still possible if the epoch is a public counter. An attacker can bank several weeks of compute and spend it in one week. Only an unpredictable beacon prevents this, and RNS has no consensus to supply one, so this report accepts it as a bounded one-TTL burst ([SybilControl](https://arxiv.org/abs/1201.2657)). Most Raspberry Pis lack a battery-backed clock and offline meshes have no NTP, so a server whose clock it cannot trust should fall back to local expiry. It holds a verified stamp for one epoch of its own uptime, then requires a higher epoch number from that publisher. A wrong clock then fails safe: the publisher drops into the unstamped shares.

Even a recurring stamp does not make flooding expensive. Laurie and Clayton's calibration study found that a puzzle hard enough to stop spammers also blocks 1.6–13% of legitimate users, because legitimate demand has a long tail and attackers rent fast hardware. Their conclusion was that plain per-item PoW "is not a solution" without reputation or whitelisting ([Laurie & Clayton, WEIS 2004](https://www.cl.cam.ac.uk/~rnc1/proofwork2.pdf)). Liu and Camp's rebuttal is the design rnfs needs: PoW works when only unknown, low-reputation senders pay ([Liu & Camp](https://archive.nyu.edu/bitstream/2451/28461/2/Camp_06-18.pdf)). The figures below apply the roadmap's calibration ("1000 extra records cost a few minutes on one desktop core", taken as 3 minutes) to an RTX 4090 rented at about $0.30/hour ([computeprices](https://computeprices.com/providers/vast/gpus/rtx4090), [Hostinger](https://www.hostinger.com/au/tutorials/?p=150400)). GPU rates come from hashcat ([Chick3nman 4090 benchmark](https://gist.github.com/Chick3nman/32e662a5bb63bc4f51b847bb422222fd)). Honest CPU rates are a local benchmark from this research (Ryzen 5 7600X, Python 3.12 `hashlib`, unpublished). All derived figures are this report's arithmetic.

| Stamp function | Honest desktop core | RTX 4090 | GPU edge per core | Attacker time for a 100k-record allowance | Attacker cost |
|---|---|---|---|---|---|
| SHA-256 (roadmap) | ~3.5 MH/s (Python loop) | 21,975 MH/s | ~6,000x | ~3 GPU-seconds | ~$0.0003 |
| scrypt N=2^14, r=8 (16 MiB) | ~35 evals/s | ~7,126 evals/s | ~200x | ~90 GPU-seconds | ~$0.007 |

Those costs are per epoch. Stamps are portable, which was the roadmap's reason for them ("a stamp is verified by any server on its own"). Portability also means **the same allowance applies at every server at once**. The research notes estimated the cost as "per server attacked", but that understates the reach. One week's sub-cent stamp lets an attacker fill its stamped share on every server whose keyspace it targets. What still grows with the number of servers is the attacker's bandwidth, not its compute. Raising difficulty does not escape this: in the resource notes' stricter c0=17 scrypt example, filling 100k records costs about $1.50 of GPU time, and an honest Pi publisher is priced out long before a GPU renter notices. PoW is therefore a **weighting signal, not a barrier**. It makes a stranger's share proportional to recurring work, but it cannot protect anyone's records by itself.

Among stamp functions, **scrypt is the only practical memory-hard choice** for 0.2.0. It cuts the GPU edge about 30-fold relative to SHA-256 (the hashcat run does not state r, so treat this ratio as approximate). It is in Python's standard library, its proof is just a nonce, and it verifies in 16 MiB, which fits a Pi Zero 2. Pi verification time has not been measured. The resource notes estimate 0.1–0.3 s, which is acceptable once per publisher per server per epoch with caching. Each trial must rebuild the whole scrypt state with the nonce inside the password or salt, so the LXMF-style midstate shortcut cannot apply. The alternatives each fail a hard constraint:

| Option | Proof size | Verifier cost | Standard library | Fit for rnfs |
|---|---|---|---|---|
| scrypt | 8–16 B nonce | 16 MiB, one evaluation | Yes | Best available |
| Argon2 / Balloon ([ePrint 2016/027](https://eprint.iacr.org/2016/027)) | Nonce | Similar to scrypt | No | Adds a dependency; published attacks on both |
| Equihash ([ePrint 2015/946](https://eprint.iacr.org/2015/946)) | 120–1,344 B | Cheap, asymmetric | No | Proof costs 1–11 s of LoRa airtime |
| Cuckoo Cycle ([tromp/cuckoo](https://github.com/tromp/cuckoo)) | ~168 B | 84 siphashes | No | Native solver; GPU about 10x faster |
| RandomX ([README](https://github.com/tevador/RandomX)) | Nonce | 256 MiB light mode; a Pi 3 does 20 H/s | No | Too heavy; needs a global rotating key |
| Chia proof of space ([docs](https://docs.chia.net/proof-of-space)) | Small | Cheap | No | ~101 GiB plot; cheap for attackers, scarce for Pis |

Proof of contribution ("pay by serving") is attractive because it is recurring and useful. But no source describes a way to verify it cheaply over low-bandwidth links, and audits cost airtime. It belongs as a locally observed reputation input, not as a verifiable proof.

## RNS shows location only to servers that own their ingress

IP diversity works elsewhere by changing the attacker's unit of cost from "one keypair" to "one routable prefix". libp2p groups IPv4 by /16 or legacy /8 and IPv6 by ASN, and allows 2 per bucket and 3 per table ([peerdiversity filter](https://raw.githubusercontent.com/libp2p/go-libp2p-kbucket/master/peerdiversity/filter.go)). geth allows 2 per /24 per bucket and 10 per table ([table.go](https://raw.githubusercontent.com/ethereum/go-ethereum/master/p2p/discover/table.go)). BEP 42 admits that "controlling IPs still grows an attacker's influence linearly" ([BEP 42](https://www.bittorrent.org/beps/bep_0042.html)). Kohnen et al. bypassed eMule's /24 checks by inserting a single Sybil that chains lookups onward. They concluded that "if the attacker controls nodes in different IP subnets, these checks would not help" ([IFIP Networking 2009](https://networking.ifip.org/2009/Website/proceedings/networking/1569170497.pdf)). None of these systems applies location diversity to a record store. An rnfs location-keyed record cap would go beyond prior art, and there is no field data on how it performs.

The installed RNS 1.5.6 source shows that what a server can see depends on topology. `link.attached_interface` is the local interface a link request arrived on, pinned for the link's lifetime (`RNS/Link.py:210`, `RNS/Link.py:939`):

| Server topology | What `attached_interface` identifies | Usable fairness key | Cost for the attacker to multiply it |
|---|---|---|---|
| Own instance, TCP or Backbone server | A sub-interface created per connection, carrying the peer IP (`TCPInterface.py:587-650`, `BackboneInterface.py:681`) | (parent interface, IP prefix /24 or /48) | Buy IP prefixes, as with libp2p or geth |
| Own instance, outbound client to a public hub | The hub | One key for everyone behind the hub | Free |
| LoRa / RNode | One interface per radio (`RNodeInterface.py:1254`) | One key per channel | Must be in RF range, or bridge in |
| I2P | A sub-interface per peer, with no address (`I2PInterface.py:822-835`) | One key for all I2P traffic | Free |
| AutoInterface (LAN) | A sub-interface per link-local address | Per address | Cheap on the same segment |
| Client of a shared instance (rnsd) | Always the one `LocalInterface` | None | Not applicable |

Hop count cannot fill the gap. It is an unauthenticated header byte that the originator sets. RNS itself randomises it to 2–7 for shared-instance clients via `local_hops_delta`. The last transport node strips the transport ID before delivery (`Transport.py:337`, `Transport.py:2032-2036`). A server therefore never learns which relay forwarded a link request, and "per path" or "per transport node" cannot be an unforgeable key.

Location becomes useful through two-level max-min fairness: share the store among ingress keys first, then among identities within each key. CAKE's `dual-srchost` mode does this for bandwidth ([tc-cake(8)](https://man7.org/linux/man-pages/man8/tc-cake.8.html)), and Bitcoin's addrman does it for addresses by source netgroup ([addrman.cpp](https://raw.githubusercontent.com/bitcoin/bitcoin/master/src/addrman.cpp)). An attacker on one key gets at most that key's share, but honest identities on the same key are diluted to share/(n+S). The common internet case is a Pi running as a leaf behind one public hub, or as a client of rnsd. There the hierarchy collapses to a flat per-identity cap, which is useless against Sybils. RNS's own ingress control is the right precedent in spirit. It works per sub-interface and gives interfaces younger than `IC_NEW_TIME` = 2h a stricter threshold. But it limits only the *rate* of announces for unknown destinations, not the *state* held (`Interface.py:76-84`, `Transport.py:1802-1826`; [Reticulum manual](https://reticulum.network/manual/interfaces.html)). Location is therefore a best-effort partition that applies only to servers running their own RNS instance with inbound listeners. It is never the primary key.

## Observer-anchored trust holds; global reputation and seniority do not

The academic social-graph defences have the strongest theory and no deployments. SybilLimit accepts O(log n) Sybils per attack edge, about 10 per edge in a million-node experiment ([SybilLimit](https://www.comp.nus.edu.sg/~yuhf/yuh-sybillimit.pdf)). Whanau gives a Sybil-proof DHT whose guarantee depends only on attack edges, and its layered IDs defeat clustering near a key ([NSDI'10](https://www.usenix.org/conference/nsdi10-0/wh%C4%81nau-sybil-proof-distributed-hash-table)). Both assume a fast-mixing honest graph with few attack edges, and measurements break both assumptions. Real social graphs mix far more slowly than assumed ([Mohaisen et al., IMC'10](https://seal.cs.ucf.edu/doc/imc10.pdf)). These schemes reduce to local community detection, which misclassifies honest outsiders ([Viswanath et al., SIGCOMM'10](https://www.mpi-sws.org/%7Egummadi/papers/comm318g.pdf)). And over 70% of 650k real Renren Sybils had no edges to other Sybils: they collected attack edges by befriending popular users ([Yang et al.](https://arxiv.org/pdf/1106.5321)). For rnfs, SybilLimit would need about 70 random walks of 10–15 hops per node at n=5,000, roughly 350k messages per refresh. That rules it out over LoRa. An rnfs contacts list is also one-sided, unsigned and private, so it is not the mutual trust graph these schemes need.

What does work in practice is trust that is personal and limited in hops, judged from the observer's own position. Nostr WoT relays accept only pubkeys within N follow-hops of the operator, and users report the spam disappears ([OpenSats](https://opensats.org/topics/web-of-trust)). Scuttlebutt replicates only within the follow graph ([Scuttlebot](https://viewer.scuttlebot.io/%25llhktDf9cwF04FX1r8bYrAR9eH%2F%2BTVMUFF7ZAl77Q9Q%3D.sha256)). Freenet gates newcomers to zero trust through captchas ([Freenet WoT](https://github.com/freenet/wiki/wiki/Web-of-Trust)). Theory agrees. Cheng and Friedman show that a symmetric reputation function, the same for every observer, can always be manipulated by Sybils, while some asymmetric flow-based functions computed from the observer's position cannot ([Stanford abstract](https://or.stanford.edu/seminars/friedman_111605.html)). EigenTrust, a global reputation scheme, "does not work against sybils" ([Traupman, Berkeley EECS-2007-75](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2007/EECS-2007-75.html)). **The operator's contacts, allowlists and private-mode members are the one Sybil-proof resource rnfs already has.** Each server judges them from its own position, and an attacker cannot mint them. A one-hop signed vouch extends this cheaply: about 100–150 bytes, with a short expiry, and all of a voucher's vouchees sharing one quota. That last rule is SumUp's "cap per attack edge, not per identity" reduced to a single hop ([SumUp](https://cs.nyu.edu/~lakshmi/nsdi09.pdf)).

Seniority is a speed bump, not a defence. Tor's 96-hour HSDir and 7-day Stable thresholds work only because directory authorities pair them with at most 2 relays per IP and bandwidth they measure themselves ([Tor dir-spec](https://spec.torproject.org/dir-spec/assigning-flags-vote.html)). IPFS's "keep reachable incumbents" rule worked alongside an IP-diversity cap ([IPFS DHT hardening](https://blog.ipfs.tech/2020-10-30-dht-hardening/)). rnfs's one-day ramp costs an attacker one day of waiting and nothing per identity: create 10,000 identities, announce once, wait. "Older evicts newer" then protects the pre-aged Sybils against honest newcomers. Signed first-seen attestations would make seniority portable when K-closest sets drift. But they prove age, not uniqueness: 10,000 identities attested on the same day are all senior. Weighting attestations by the attester's standing turns into EigenTrust-style recursion. Seniority still earns a place, for two reasons. It is cheap and needs no wire changes. And when it requires observed activity on several distinct days, rather than one sighting a day ago, it forces the attacker to commit identities ahead of time and keep refreshing them. Within the senior tier, eviction should be max-min fair rather than strictly age-ordered, so pre-aged Sybils get N/(N+H) of that tier and not all of it.

## Publish caps stop storage exhaustion, not eclipse

A per-publisher cap protects one thing: honest servers' stores against exhaustion and eviction of honest records. It does nothing when the attacker *is* the K closest servers for a key. Prünster et al. eclipsed go-ipfs nodes in under an hour with about 75% probability, needing only the target's ID (CVE-2020-10937). The fixes that worked were all at the routing layer ([arXiv 2011.00874](https://arxiv.org/pdf/2011.00874), [IPFS blog](https://blog.ipfs.tech/2020-10-30-dht-hardening/)). Sridhar et al. censored CIDs by grinding Sybil IDs next to them ([arXiv 2307.12212](https://arxiv.org/pdf/2307.12212)). A 2025 active-Sybil study placed about 14 Sybils per target from one public machine. Retrieval success dropped to 18% under the detection-based mitigation and 28% under the authors' own SR-DHT-Store. Disjoint lookup paths restored 100% at about 2.5x the lookup cost (55.7 versus 21.9 nodes contacted) ([arXiv 2505.01139](https://arxiv.org/html/2505.01139v1)). KAD publication eclipse needs only 10 Sybils, because KAD stores on 10 nodes ([Kohnen et al.](https://networking.ifip.org/2009/Website/proceedings/networking/1569170497.pdf)). rnfs has the same K=10. Grinding RNS identities near a target costs one keypair and one hash per try; this has not been benchmarked here, but it is plainly cheap.

| Attack | Does a per-publisher cap help? | What defends instead |
|---|---|---|
| Storage exhaustion and eviction of honest records on honest servers | Yes, bounded by identities × cap | Trust-tiered floors, newcomer pool, fair eviction, recurring stamps for strangers |
| Key eclipse (about 10 ground IDs nearest a CID) | No | Query beyond K (2K–3K), disjoint paths, seed lookups from contacts, treat "no providers" from the K closest as inconclusive |
| Routing-table pollution | No | Keep live incumbents, per-interface diversity in buckets, prefer contacts |
| Query flooding and LoRa airtime exhaustion | No | Per-interface and per-neighbour rate limits, RNS ingress control, response caching |
| Fake providers crowding one CID | Partly | A per-CID provider cap that prefers senior and trusted providers ([libtorrent caps peers per infohash at 500](https://www.libtorrent.org/reference-Settings.html)); clients verify content by hash |

rnfs's random-half selection of `/find` replies stops a single bad hop from steering a lookup. It does not help when the whole K-set at the destination is Sybil, which is exactly the grinding case. Eclipse defence therefore belongs in the lookup roadmap, not in the publish-cap design. Mixing the two would make the cap seem to promise more than it can deliver.

## A four-tier allowance fits 0.2.0 with no wire change beyond `/stamp`

The recommendation is a hierarchical fair share. Fairness is computed over *trust classes* first and individual publishers second, so a Sybil flood competes only inside the classes it can enter. Each tier has a guaranteed floor of `max_records`. Unused floor is lent to anyone while the store has room, which keeps the roadmap's "free space" behaviour. When the store is full, borrowed space is reclaimed first, from the publisher furthest over its share. The floor percentages below are illustrative defaults for the 100k-record case. They have not been tuned by simulation.

| Tier | Who qualifies | Evidence | Floor (of 100k) | Per-publisher entitlement | Evicted by lower tiers? |
|---|---|---|---|---|---|
| T: trusted | Operator contacts, allowlisted nodes, private-mode members | Local configuration | 30% | Up to `max_records/10` | Never |
| S: senior | Seen by this server refreshing on at least 3 distinct days (today: first seen at least 1 day ago) | Local observation, persisted with the routing table | 40% | `max_records/100` (1000), max-min fair within the tier | Never |
| W: stamped | Valid scrypt stamp for the current or previous 7-day epoch | `/stamp`, verified once per epoch and cached | 20% | `max_records/100 × 2^(c − c0)`, scaled down pro rata to work when the tier is oversubscribed | Only within W |
| N: newcomer | Everyone else, including 0.1.x publishers | None | 10% (today's pool) | `max_records/1000` (100) | Only within N |

A publisher's entitlement is its highest tier's floor share, and any extra it buys with a stamp counts against tier W. A senior heavy publisher therefore keeps its 1000 protected records, while its stamped extra competes only with other stamped strangers. Concretely, the 0.2.0 "Publisher stamps" item changes in five ways. The one-time SHA-256 stamp becomes an **epoch-bound scrypt stamp** (N=2^14, r=8, p=1, with the epoch and nonce inside the hashed input). Servers accept the current and previous epoch, and fall back to local expiry when their clock is not trustworthy. The per-stamp ceiling drops from `max_records/2` to the tier W budget. The grant per stamp bit falls as tier W fills, which is the occupancy-priced admission of discv5 ([discv5-theory](https://github.com/ethereum/devp2p/blob/master/discv5/discv5-theory.md)) and NIP-13's committed difficulty ([NIP-13](https://github.com/nostr-protocol/nips/blob/master/13.md)); it needs no extra wire field, because `/stamp` already answers with the limit granted. And scrypt verifications are rate-limited per link and globally, because each one costs a Pi a fraction of a second. `/stamp` has not shipped yet, so choosing scrypt and epochs now costs nothing in compatibility and avoids a later "stamp v2". The rest is local policy with no wire change: the trust-class floors, max-min fairness within tier S in place of strict older-evicts-newer, the stricter seniority test, and a per-CID provider cap of about 50 that prefers trusted and senior providers.

A 0.1.x publisher never sends `/stamp`, so it lands in N or S exactly as today. A 0.1.x server ignores `/stamp`, and the publisher remembers that after one timeout, as the roadmap already specifies. Ingress-location partitioning comes later as an optional refinement within tiers W and N. It would key on (parent interface, IP prefix) only on servers with their own instance and inbound listeners. It is left out of 0.2.0 because most deployments would gain nothing from it.

Network size changes which tier does the work:

| | Small LoRa mesh (tens of nodes) | Thousands of internet nodes |
|---|---|---|
| Binding attacker constraint | Airtime: at about 40 bytes per key, 100k records is about 4 MB, roughly 9 hours of continuous 1 kbit/s airtime (this report's estimate) | Compute and bandwidth are cheap; a stamped share costs under a cent per epoch |
| Tier doing most of the protecting | T and S: everyone knows everyone, and operators can list each other | S and T; W serves honest heavy strangers in peacetime |
| Stamps | Rarely needed; Pi publishers stay within seniority shares | Needed by large publishers whose keys drift to servers that do not know them |
| Location | One key per radio. A server with both an RNode and a TCP interface can keep internet traffic from crowding out radio-local publishers. A bridge node on the same channel collapses everything to one key | Useful only on servers that accept inbound TCP; leaves behind a hub and rnsd clients get nothing |
| Residual risk | A bridged-in flood fills W and N on mesh servers | A patient attacker saturates S with pre-aged Sybils and W with GPU stamps; T is untouched |

The trade-offs are explicit. The trusted tier makes rnfs less open to newcomers who have no contacts, which is Nostr's echo-chamber cost. Tier W gives honest strangers little under a determined GPU attacker. Epoch stamps cost an honest heavy publisher on a Pi recurring background CPU, about one stamp per week. Lower-tier floors can be raised only at the expense of what the operator's own trust list is guaranteed. Three gaps need closing before the parameters are frozen: scrypt verification time on a Pi Zero 2 and a Pi 4 is unmeasured; no simulation yet pits a GPU attacker against a mixed Pi and desktop honest population under these tier floors; and nobody has measured how quickly RNS identities can be ground near a target key, which sizes the lookup-side eclipse work. The later roadmap work is one-hop vouches (tier T extending quota to vouchees under a shared budget) and lookup hardening: querying 2K–3K nodes, disjoint paths, and lookups seeded from contacts.

## Conclusion

The stamp's real job differs from the one it was proposed for. It is a poor Sybil barrier, because one GPU-week costs under a cent and every server honours the result. It is a good admission ticket for an honest heavy publisher arriving at servers that have never seen it, which is the drift problem the roadmap set out to solve. Framed that way, the design questions shift. The question is no longer "how hard must the puzzle be?" but "how much of the store may strangers who pay be allowed to take?" The answer to that is a policy floor, not a difficulty number. Sybil resistance in rnfs comes almost entirely from structure: partitions anchored in what each server knows first-hand, which Sybils can fill but never cross.

This also clarifies what rnfs can claim. In a network of free identities with no IP layer, no design bounds an attacker's total footprint. The achievable guarantee is narrower and still worth stating: **records from publishers a server's operator trusts, or has watched for days, survive any flood**, and everything else degrades in proportion to what the attacker pays continuously. Eclipse resistance is a separate promise, to be earned in the lookup path.
