## Sanity check findings

Numbered as in the handoff. "Roadmap fixed" means the change is in `roadmap.md` (commit listed under Done).

### 1. Clients stop announcing `rnfs.dht`

- **Wrong fact in the plan.** RNS answers a path request for a local destination with a fresh announce
  carrying the default app_data (`Transport.path_request` → `Destination.announce(path_response=True)`; rnfs
  sets the mode as default app_data since 0.1.0, `announces.py`), but a transport node that has no path
  forwards the request only if it arrived on an interface with `recursive_prs`, in a `DISCOVER_PATHS_FOR` mode
  (access point, gateway, roaming, internal), a boundary interface, or from a local client; otherwise it logs
  "Ignoring path request … no path known" and drops it (RNS 1.5.6 `Transport.py` ~3426–3590). The default mode
  is `full`. Transport nodes keep a path `PATHFINDER_E` (7 days; 1 day on access-point interfaces, 6 h on
  roaming ones) after the announce, refreshed only by traffic. So a client that never announces is reachable
  only from one hop away or through favourable interface modes: 0.1.x (and 0.2.0) fetchers couldn't get its
  blocks (`LinkPool._open` awaits a path, then `Identity.recall`), nor send it `/pin` or `/name` (its own names'
  keeper).
- Private mode: 0.1.4–0.1.6 servers drop at every start the records of publishers whose identity RNS doesn't
  recall (`records.retain(_is_member_publisher)`), and RNS forgets unused pathless identities after 6 minutes, so
  non-announcing private-mode clients would lose their records at every server restart.
- Peers: clients would vanish from servers' `rnfs peers` (fed by announces); `contacts add` can't detect the
  kind of a destination never heard. Routing tables, the join and LXMF don't use client announces.
- **Fix (roadmap updated, conservative):** a client announces `rnfs.dht` at startup (and after
  `startup_announce_delay`, and on a mode change) as today, and then every `announce_interval` only while
  something needs it reachable: it provides anything (records out, kept names), accepts remote pins, or is in
  private mode. A client that only fetches stops its periodic announces. Stretching the providing client's
  interval (paths last 7 days in `full` mode, but 6 h on roaming interfaces) is a question for the owner (Q2).

### 2. Names announced only when they change

- **Wrong mechanism.** The owner does answer path requests with a fresh announce, but the nearest transport
  node holding a path answers first from its cache with the old announce and its old emission time, and once
  paths lapse (7 days, less on access-point/roaming interfaces; name destinations carry no traffic to refresh
  them) the request no longer reaches the owner in `full` mode (as in 1).
- **Breaks 0.1.5+ resolvers' cost.** Since 0.1.5 an announce shows its record current only for
  `ANNOUNCE_VALIDITY` (2) × `announce_interval` after it was emitted (`names._announce_heard`; spec section 9
  "ask keepers if … heard only an announce emitted more than 2 × `announce_interval` ago"). A record unchanged
  for 12 h would make every network resolve of a 0.1.5/0.1.6 node (CLI resolve, gateway at most every 60 s per
  name, follow and deny every 12 h) add a keeper query, ten to twenty times the airtime of a path-answered
  resolve. The record is still returned, so it is a cost, not a failure; 0.1.3/0.1.4 have no cap.
- "Keepers first" is in effect `keeper_query = always`, which the spec says SHOULD NOT be used on slow links:
  on LoRa it may cost more airtime than the announces it saves.
- Keepers themselves don't need periodic announces (kept records don't expire; refreshed on a higher sequence or
  a later emission of the same record).
- **Fix (roadmap updated, conservative):** name announces stay every `announce_interval` in 0.2.0, plus one on
  every change as today. "On change only" and "keepers first" move to *After 0.2.0*, for when 0.1.5/0.1.6
  resolvers are gone (their validity rule is what needs the periodic announce). Stretching the name announce
  towards 2 × `announce_interval` (e.g. 10 h at the default) is possible but fragile against resolvers with a
  shorter `announce_interval`: question for the owner (Q3).

### Partition mode's silence trigger (found while checking 5 and 6)

- "~10 minutes without an off-island announce" assumes a busy network. With servers announcing every 6 h, an
  island that hears 20 off-island servers hears one about every 18 minutes, so it would enter partition mode
  (lookups and publishes local only) while connected, and flap. **Fix (roadmap updated):** enter partition
  mode on 3 failures in a row reaching off-island servers; silence counts only once it exceeds 4× the usual
  gap between off-island announces this node has measured (and at least 10 minutes).

### 3. Newcomer records expiring after 4.5 days

- Spec section 6: a record expires `PROVIDER_TTL` after it was last stored, and `republish_interval` MUST be
  below `PROVIDER_TTL / 2`, so a record survives one missed republish. Any honest node, 0.1.x included, may set
  `republish_interval` up to just under 3.5 days; kept names republish at max(interval, 3 days) ± 10%, capped
  below 3.5 days − 1 h (`publisher.key_interval`); slow nodes pace lookups (10 per round, 30 s × n after a round)
  on top. So the longest honest gap is just under 3.5 days plus pacing and downtime, and 4.5 days leaves about a
  day of margin, as the storage simulation's E4 measured.
- But a shorter expiry applied always (as simulated) takes away the "survives one missed republish" property
  from every Newcomer-tier record in peacetime: a slow or name-keeping publisher whose republish misses this
  server once (server unreachable that round, a different closest set, a restart at the wrong time) loses the
  record here at 4.5 days instead of 7, with nothing gained, since an unfull store has no one to make room for.
- **Fix (roadmap updated):** the 4.5-day expiry applies only while the record budget is full, like the rest of
  the tiers ("applied only once the record budget is full"); it is then one more way the tiers make room, which
  the spec already allows (records are evicted when the store is full). In peacetime every record lives
  `PROVIDER_TTL`. A flood fills the budget, so flood recovery is as simulated. The spec states it as local server
  policy under section 6's "Provider records", next to eviction, and `PROVIDER_TTL` stays 7 days.

### 4. The record budget replacing `max_records`

- `max_records` is read in one place (`node.py`, `ProviderStore(config.max_records, ...)`); its other uses are
  `config.py` (field, range, help text), spec section 6 and 12, design.md, and two CHANGELOG lines of past
  releases (left as history).
- `Config.combine` raises on any unknown key, so a `max_records` left in `rnfs.toml` would stop the daemon.
  Plan: a `RETIRED_SETTINGS` set in `config.py`, dropped from the values with a warning through the existing
  `Config.warnings` list (the daemon logs them). The same mechanism takes the `lxmf_*` settings when LXMF leaves
  core. `rnfs config set max_records` is refused as unknown; the settings API's schema no longer lists it.
- The roadmap's default ("e.g. 1 GiB") needs a number and a name: **`record_budget`, default 1 GiB**, never
  more than the free disk above the blocks' reserve (max(256 MiB, 2%)). The 117 bytes per record on disk come
  from the load study; SQLite's B-tree overhead and the indexes the tiers need will raise it, so the budget is
  measured from the database (records × measured bytes per record, recomputed periodically), not assumed.
- Per-publisher caps, the newcomer pool and the departed/evicted memories go; their four tables stay (released
  schema) but are migrated by a new schema step into the new layout and then left empty.

### 5. One publish procedure for sweep providing and everything that adds stores

The roadmap describes six things that each add stores per key, in four sections, without saying how they
combine. Today (`publisher.publish_due`): one closest-nodes lookup per due item (4 at once; 10 per round, 30 s
× n apart on slow nodes), then one identified link per node carrying its keys and withdrawals in batches
(`protocol.provide_batches`, withdrawals first), stopping at the first refused batch. Withdrawals are sent at
once, unpaced. The combined round, as written into the roadmap ("Providing at scale", "One publish round"):

1. **Due set.** Due keys (CIDs, DhtKeys, entry keys of `provide_entries`) and queued withdrawals. On slow nodes
   the round's budget counts lookups (regions), not keys: at most 10 region lookups per round, 30 s × n after.
2. **Regions.** Sort the due keys. For the first key x not yet covered, run the closest-nodes lookup as `d`
   disjoint paths (3 on fast nodes, 2 on slow; S/Kademlia), merged, with up to 10 path requests per lookup on
   slow nodes. In partition mode the lookup uses local servers only. p = common prefix of x and its 10th-closest
   merged result; the region is every due key sharing x's first p bits; if it has 2 or more, one `/find` to the
   known node nearest the centre of its far half (each half again if that reply is full).
3. **Per key, from what the region learned** (no further lookups unless step 3b fires):
   a. the `K` closest;
   b. the density check, per key over the region's merged nodes (the size estimate comes from the last ~16
      lookups for other keys). A key it flags gets a lookup of its own, widened in the two rings, and stores to
      `K` more per ring. Sybils ground next to one key sit inside its region, so the region's nodes show them.
      Expected cost: the 4% false-positive rate means about 1 extra lookup per 25 keys flagged, not per region,
      so it is bounded per round like the other lookups (fast: counted in `PUBLISH_LOOKUPS`; slow: in the
      round's 10).
   c. the `K` closest servers in the announce first-seen log first heard at least `provider_seniority` ago
      (local, no lookup; mostly the same as a.);
   d. the 3 closest local servers (two-level records; local, no lookup);
   The key's store set is the union, without duplicates.
4. **Batches.** Group store sets by server; each server's queued withdrawals ride first in its batches, as
   today. One identified link per server per round (unchanged), `/provide` sent to 8–16 servers in parallel on
   fast nodes, one at a time on slow ones. Every server stored to is recorded in `published`/`published_earlier`
   (already the case for whatever nodes a round sends to), so withdrawals reach ring, senior and local stores.
5. **Withdrawal-only servers** are sent in the same round; on slow nodes they are paced too, counted as one
   lookup's worth of budget per server (today they are unpaced: spec section 6 says "Withdrawals are not
   delayed by this", which changes to a SHOULD pace).
6. **After the round:** keys whose round reached no off-island server are marked for the heal republish;
   jitter is per region, so a region's keys stay due together.

**Airtime on a slow node** (1 kbit/s, figures from the load and topology studies: `/find` exchange 4.0 s,
identified link 6.4 s, path request 2.6 s, a perfectly batched key 2.63 s for `K` stores): per region about 2
disjoint lookups × 3.4–4.7 `/find` + 1.6 extra ≈ 34–44 s, plus path requests (up to 10, typically a few); per key
2.63 s × (10 + ~2 senior extras + 3 local) / 10 ≈ 3.9 s, ≈ 7 s for a key the density check flags; per server
contacted per round 6.4 s. The roadmap's capacity table (4,500 keys at 100 servers, 590 at 1,000, 111 at 10,000,
at 5% of the channel with a 72 h republish) was computed for `K` stores per key and one lookup per region: with
the extras, expect about two thirds of those numbers. `provide_entries` on slow nodes uses the same estimate
(on only while it stays under ~2% of the channel).

### 6. "Local" on a shared instance

- Works, mostly with what exists. Hop counts in a client of rnsd equal the instance's (RNS adds and removes the
  shared-instance hop symmetrically; path responses to clients carry the stored count). The next-hop interface
  is the client's `LocalInterface`, but the instance's real one comes over RPC: `get_next_hop_if_name`,
  `get_path_table(max_hops)`, `get_interface_stats` (short name, bitrate). `rnfs/mesh.py`'s `RnsPaths` already
  uses them for provider ranking and `rnfs peers`; slow-node detection (`rates.is_slow_node`) already works
  through the instance.
- Gaps: (a) a client's path table starts empty (and is wiped on reconnect), and `RnsPaths.infos()` checks the
  local `has_path` before asking over RPC, so a newly started node sees no hops for most nodes rnsd knows: the
  local-server set is built from one `get_path_table(max_hops=local_hops)` call at start, refreshed
  periodically. (b) Local is judged from the path to a node, never from the interface a request arrived on
  (always the local one). (c) `local_interfaces` names the instance's interfaces as rnsd's config names them,
  matched like `serve_interfaces`. (d) The roadmap's "4 hops starts counting backbone nodes behind the gateway"
  understates it: a node one LoRa hop from its gateway reaches servers on the gateway's internet hub in 3 hops
  over a slow first hop, so with a big public hub they can be most of the "3 closest local servers". The
  simulation's 98–100% is findability, which hub servers still give while connected. Kept `local_hops = 3`
  and documented: set `local_interfaces` (or a lower `local_hops`) on islands whose gateway hangs off a big hub.
  If the instance can't be asked, nothing is local. Roadmap updated.

### 7. Demoting slow-path servers on fast nodes

- Signals: hops need a path-table entry (no RPC needed for the count); RTT exists only for links this node
  opened (`LinkPool.on_rtt` → `Traffic.measured`, in memory, LRU of 1000 peers, lost on restart). RTT is
  measured by the initiator, so only an on-path transport node can inflate it (by delaying the proof), and only
  an on-path node can raise a hop count (announce signatures don't cover hops); either could already drop the
  traffic. A popular hub could demote everyone behind it, but demotion is ordering only.
- I2P: RTT over I2P is often above 1 s and its links stay at MTU 500, so an RTT rule alone would demote I2P
  backbone nodes that cost no radio airtime.
- **Rules (roadmap updated):** fast nodes only; only the order of lookup queries (closest-nodes and
  providers), the way `unreliable` works, never the routing table, `/find` replies, provider ranking or failure
  counts. Slow path = RNS path of more than 3 hops, or this node's last own link to it (within 24 h) had RTT
  above ~1 s **and** a rate estimate below `slow_bitrate`. Unknown (no path, no measurement) ranks normally.
  Rank tiers: answered or fast/unknown, then slow path, then unreliable; by distance within a tier. Still
  asked when too few others remain, and still fill `K` for stores.

### 8. NomadNet add and the process-wide decompression limit

- The limit is per Resource: `Resource.__init__` copies `AUTO_COMPRESS_MAX_SIZE` into
  `self.max_decompressed_size`, which `assemble` reads (RNS 1.5.6 `Resource.py` 368, 700). Response Resources
  pass through `Resource.accept`, which calls the link's `resource_started` callback before any data arrives;
  rnfs's LXMF feature already sets `max_decompressed_size` there (`features/lxmf.py` ~2044, ~2254).
- RNS never checks the decompressed size against the advertised `d` (only the hash), and doesn't check segment
  sequence (`i`, `l`): a malicious node can keep sending segments.
- **Mechanism (roadmap updated):** rnfs opens NomadNet links itself; requests carry `max_response_size` =
  min(`max_download_size`, free space above the disk reserve); a `resource_started` callback on that link sets
  `max_decompressed_size` to `MAX_EFFICIENT_SIZE + 1` per segment and requires the same original hash and `d`,
  `i` = previous + 1 and `l` = what an honest sender computes from `d`, else cancels and tears the link down;
  the assembled file is checked to be no larger than `d` and copied into storage inside the response callback
  (RNS deletes it after). Page responses must be one flat byte string, checked from the msgpack headers before
  RNS decodes them (the `rnfs.dht` response check, extended to these links). `rnfs.dht` links are unchanged.

### 9. Gateway subdomains and base36

- Spec section 4: "every CID has exactly one written form" (`b` + lowercase base32, canonical round trip);
  `Cid.parse` accepts nothing else, so a base36 form can't leak in through any existing parser.
- Lengths: `k` + base36 of the binary CID is a fixed 56 characters (raw) or 60 (rnfs-dag): both fit a DNS
  label. Names are 32 hex characters (fit; browsers lowercase hosts, and `parse_hex16` accepts either case).
- **The plan as written does nothing:** every gateway response carries `sandbox allow-scripts …` without
  `allow-same-origin` (`gateway.CSP_SCRIPTS`), so the page has an opaque origin and its own `fetch()` is
  cross-origin with `Origin: null`. Subdomain hosts need `sandbox allow-same-origin …` (the path gateway keeps
  today's CSP).
- Browser facts the plan misses: `localhost` is not on the Public Suffix List, so every `*.rnfs.localhost` site
  is the same *site*: cookies (which ignore ports) are shared between sites; localStorage/IndexedDB are per
  origin. `http://*.localhost` is a secure context, so pages could register service workers (on
  `<name>.name.localhost` one could keep serving old content after a republish). Only some resolvers map
  `*.localhost` to loopback (Chrome and Firefox do internally; OS resolvers vary).
- **Fix (roadmap updated):** base36 is a host-only encoding, accepted only by the gateway's host parser, exact
  length and canonical, converted to the base32 CID before any other use (spec section 4 says so next to the
  one-written-form rule). The API's exact Host check (`host_allowed`) is not widened; the gateway gets its own
  host parser. Subdomain responses: `sandbox allow-same-origin allow-scripts allow-forms allow-popups` (no
  `allow-scripts` with `gateway_scripts` off), `Origin-Agent-Cluster: ?1`, `frame-ancestors 'self'`, requests
  carrying `Service-Worker: script` refused, `?format=` refused, empty path segments still 400 (no
  protocol-relative redirect). The path gateway stays and is the fallback; cookies being shared between sites
  is documented. Whether to allow service workers is a question (Q4).

### 10. Encrypted folders

- The sealed format needs no change: `SealingReader` streams (one segment held, unknown length works); the
  name is inside the envelope and must pass `dag.check_name` (1–255 bytes), so a folder name over 251 bytes
  can't take `.tar`: refuse rather than drop the name silently (`add_sealed_path` drops an invalid one).
- Neither "reuse" in the roadmap holds literally: the tar writer (`tarstream.plan`/`chunks`) walks a *stored
  DAG*, not a local folder, and puts the folder's contents at the top (so `tar xf` on 0.1.x spills into the
  current directory); the tar reader (`build_tar`) builds a DAG, it doesn't write files.
- `cat` and `GET /api/cat` already decrypt sealed files for a recipient; only the gateway never does. The
  roadmap's "`cat` and the gateway still give the sealed bytes" is wrong for `cat`.
- **Fix (roadmap updated):** packing uses a small local-folder tar writer that walks with `add`'s rules (no
  links, hard-link rules, depth and entry limits) and puts everything under one top directory `<folder>/`
  (reusing tarstream's header code). Unpacking: decrypt → `build_tar` into the block store inside a protection
  session → `walker.write_out` (get's write-out rules) → the plaintext blocks are collected afterwards; free
  space is checked for both. It unpacks only when the sealed name ends in `.tar` and the content is a valid
  tar; `--no-extract` writes the tar. `cat` gives the decrypted tar; the gateway and `--raw` the sealed bytes.

### 11. Per-app tokens, `app:` pin sources and LXMF's pins

- Pin sources are checked by `storage.check_source` (`user`, `folder`, `deny`, `name:…`, `remote:`/`follow:`/
  `lxmf:` + 32 hex), and **pin rows failing it are deleted at load**, so `app:` must be accepted before anything
  writes one. Every LXMF use goes through `storage.LXMF_PREFIX`.
- `token_valid` returns a bool and the proof is keyed on the one token, so the server can't tell which app
  called: app tokens need a persisted table (tokens must survive restarts, unlike `api_token`), a principal
  (`cli` or an app name) returned by the check, and an `X-Rnfs-App` header naming the app whose token keys the
  proof. Every path that hardcodes source `user` (add, keep, dir set/rm, pin add/rm, import, jobs replaying
  them) takes a source.
- An unconditional `lxmf:` → `app:lxmf:` rewrite while in-core LXMF still pins `lxmf:` would leak pins (inbox
  removal unpins a source that no longer exists). And `_release_unrecorded` runs even with LXMF disabled: once
  in-core LXMF used `app:lxmf:`, it would release a wrapper's pins at every start.
- **Fix (roadmap updated):** the migration runs in 0.2.0 whether or not LXMF stays (a schema step: `UPDATE pins
  SET source = 'app:' || source WHERE source LIKE 'lxmf:%'`), and in-core LXMF switches to `app:lxmf:` itself
  (`LXMF_PREFIX`). While in-core LXMF exists, `rnfs app add lxmf` is refused if it is enabled, and
  `_release_unrecorded` is skipped when an app named `lxmf` exists. `tests/test_upgrade_015.py` (its fixture has
  two `lxmf:` pins) states what those rows become. The `lxmf_messages` inbox isn't handed to the wrapper: Q5.

### 12. Block storage subdirectories

- The 2nd- and 3rd-to-last characters are full 5-bit digest digits for both codecs (raw CIDs: 59 characters,
  prefix `bafkrei`, last digit 3 bits; rnfs-dag: 64, prefix `bagaibqabciq`, last digit 2 bits): 1,024
  directories, lowercase `[a-z2-7]`, safe on case-insensitive filesystems and not Windows reserved names.
- FAT32: a 59–64-character long name takes 6 directory entries, so a directory holds about 10,900 blocks, not
  65,000 (about 11M blocks over 1,024 directories). Roadmap figure corrected. The private-directory checks need
  `uid=…,umask=077` mount options on FAT32: untested.
- Places to change: `content/blockstore.py` (`path`, the `.partial-` cleanup, `put`'s temporary file in the
  shard, `sync` fsyncing every dirty shard and `blocks/` when a shard is created, `scan` walking shards without
  following symlinks), spec (section 8), design.md, README; tests `test_blockstore`, `test_e2e` (builds
  `blocks/<cid>` by hand), `bench_block_writes`; and `test_upgrade_014/015` write blocks with the *current*
  `BlockStore`, so they'd never see a flat directory: they need a 0.1.6 flat-layout writer and half-migrated
  cases. `_warn_foreign_entries` (os.walk), free-space checks, gc, verify, `cache ls` need no change.
- Startup scan today: `BlockStore.__init__` lists `blocks/` once for `.partial-` files and `scan()` again for
  sizes (one `lstat` per block on Linux), no verification; the API binds only after `RnfsNode(config)`
  returns. The directory lock is taken first (`lock_rnfs_dir`), so the cheapest "starting" status is the CLI
  reporting the lock holder's PID when the API doesn't answer, with no reordering.
- **Fix (roadmap updated):** the move is resumable, not one-shot: every start moves any flat canonical-CID
  file into its shard (a same-filesystem rename; if the target exists, the flat copy is deleted: same content
  by CID), then fsyncs. A rename that fails (Windows antivirus) leaves the file where `path()` still finds it
  until a later start. Block sizes move into rnfs.db, committed at the existing durability point, with a
  rescan after an unclean shutdown. The Startup Scan and Block storage layout sections are merged.

### Gaps between sections (found reading the roadmap against the code)

- **Scores and provider ranking.** Spec section 6: seniority MUST stay the first key in provider ranking (an
  attacker can't make identities old). Scores can be earned quickly by serving valid blocks of popular
  content, so the roadmap's "scores order providers" means: within each seniority group, before hops. Roadmap
  updated to say so.
- **The Known tier** needs node IDs: contacts of kind `node` only (kinds `name` and `lxmf` aren't publishers).
- **Persisted routing table.** It uses `time.monotonic` and persists nothing today; first-seen and last-heard
  are stored as wall-clock times (clamped like the provider store's), so `/find` replies keep excluding nodes
  silent over 2 × `announce_interval` after a restart.
- **Kept names' jitter.** Spec section 6 gives each non-CID key a fixed ±10% jitter derived from the key, so they
  don't come due together; "jitter per region" replaces it with a jitter derived from the key's first byte, so
  keys of one region (which share their leading bits) come due together while 256 slots still spread them.

## Questions for the owner

1. Should `docs/simulations/` be committed? `roadmap.md` (committed) links to its `RESULTS.md` files, so the
   links are dead in the repository until it is. Left untracked as the handoff says.
2. Providing clients keep announcing every `announce_interval` (finding 1). Stretch it (e.g. daily, or 3 days:
   paths last 7 days in `full` mode, 1 day on access-point interfaces, 6 h on roaming ones)? A stretch saves
   client announce airtime but makes clients behind roaming/AP transport interfaces unreachable part of the
   time. Built: unchanged interval for providing clients; only fetch-only clients stop.
3. Names keep announcing every `announce_interval` (finding 2). Stretch to just under 2 × `announce_interval`
   (about 10 h at the default) while 0.1.5/0.1.6 resolvers remain? Built: unchanged.
4. Gateway subdomains: allow service workers on `*.rnfs.localhost`? They make offline-capable sites possible,
   but on `<name>.name.localhost` a worker can keep serving old content after the name moves. Built: refused
   (`Service-Worker: script` requests answered 403).
5. LXMF's inbox (`lxmf_messages` in rnfs.db): export it for the wrapper, or leave it to be dropped when LXMF
   leaves core? Built: left in place (nothing reads or deletes it once LXMF is gone).
6. LXMF removal: is the wrapper's first release ready? Until confirmed, 0.2.0 keeps LXMF deprecated (the
   roadmap's fallback).
7. `record_budget` is measured as the whole state database's size (SQLite's per-table `dbstat` is an optional
   build feature and reads every page), so other state counts against it, mostly the block-size table: about
   70 bytes per block, so a node holding 10M blocks leaves ~300 MiB of the default 1 GiB to records (~1.3M).
   Fine for typical nodes; documented. A larger default, or a separate database file for provider records, are
   the alternatives.
