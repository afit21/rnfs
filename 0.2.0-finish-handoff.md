## Rules you must keep

- **Wire compatibility.** Nodes of 0.1.3 and later must keep working with 0.2.0. Wire changes are additive only: a
  new optional request or optional behaviour, never a change to an existing message, its shape or checks, a
  protocol constant older nodes enforce (`K`, `PROVIDER_TTL`, `MAX_REQUESTS_PER_LINK`, ...), announce `app_data`,
  or the protocol aspect. `tests/test_wire.py` and its vectors must keep passing unchanged. Run
  `tests/interop.py` against 0.1.6 (CONTRIBUTING, "Tests") for anything touching the network, and always before
  you finish.
- **CIDs never change.** Chunking, `MAX_CHILDREN`, DAG encoding and codecs are fixed.
- **Upgrades must work** from 0.1.6: schema steps are append-only, after every step already in `statedb.SCHEMA`
  (CONTRIBUTING, "Adding a schema step"); the released-schema digests in `tests/test_statedb.py` never change.
- **The local API stays compatible** with 0.1.6, status codes included; new routes and fields are fine. A new
  route or status field also goes into `docs/openapi.json` (CONTRIBUTING, "Adding an API route").
- **Core vs apps.** rnfs is the core node and protocol; user-facing apps are separate projects. LXMF is gone from
  core: don't bring any of it back.
- **Commits** follow CONTRIBUTING "Commits": one change per commit, a plain summary line, a body saying what and
  why, a CHANGELOG line under `## 0.2.0 (unreleased)` for each user-visible change (put it in the section of the
  0.2.0 entry it belongs to: Security, Added, The DHT and provider records, Changed, Faster). **Never add Claude
  or AI attribution** (no `Co-Authored-By`, no "Generated with" lines) to commits or anything else in this repo.
- **Don't** push, open or merge pull requests, tag, release, or change the version number (`rnfs.__version__`
  stays 0.1.6). The owner does those.
- Don't touch `.claude/worktrees/` other than worktrees you create, `/home/afi/Documents/rnfs-ci` or
  `/home/afi/Documents/rnfs-security` (not yours), or the untracked `0.2.0-handoff.md`.
- Update `specification.md`, `design.md` and `CHANGELOG.md` with the code, and add tests. Never weaken or delete a
  test to make a change pass; a test that encodes behaviour you deliberately change is changed in the same commit,
  with the reason in the commit message.
- Mark each roadmap heading "(implemented)" once built and merged, with an "As implemented:" bullet at the end of
  the section saying what was built where it differs from or adds to the plan, and the numbers measured (as the
  other 0.2.0 sections do).

## How to work (what worked last time)

- **Tests.** Full suite: `PYTHONPATH=$PWD .venv/bin/python -m unittest discover tests > <log> 2>&1` (about 3,100
  tests, 8–17 minutes depending on load), then grep the log for `Ran [0-9]+ tests`, `OK`, `FAILED`, `FAIL:` and
  `ERROR:` without anchoring only at the start of a line (log lines can follow the summary). End-to-end:
  `RNFS_E2E=1` with the modules CONTRIBUTING lists plus `tests.test_nomadnet_e2e`. Lint: `.venv/bin/ruff check .`.
  Interop: `git archive v0.1.6 | tar -x -C <dir>`, then `PYTHONPATH=$PWD .venv/bin/python tests/interop.py --old
  <dir>` (about 5 minutes; every row must PASS).
- **`test_sweep`'s placement test is sensitive to CPU load** (thread timing of parallel region lookups): it once
  scored 0.98967 against 0.99 with six suites running at once, and passes alone. If it flakes again, run that
  test's region lookups one at a time rather than lowering its threshold.
- **Subagents** each get: this note's rules, one roadmap item (or a coherent group of bullets), their own git
  worktree, the files they may touch, and what other agents are touching at the same time. Worktrees have
  sometimes been created from `main` rather than `dev`: tell each agent to check and `git reset --hard dev` (or
  your integration branch) on its own branch first. rnfs is installed editable from the main checkout, so agents
  must run tests with `PYTHONPATH=<their worktree>`. The scratchpad is shared: give each agent its own
  subdirectory (one agent's file named `numbers.py` once shadowed the standard library module there).
- **What can run in parallel.** Items that touch `rnfs/dht/`, `rnfs/publisher.py` or `rnfs/fetcher.py` conflict:
  run those one at a time. Independent within item 1, for example: the `add` refusal and walk skip (builder,
  node, shared folder, name sync); gateway sites; NomadNet's answer cap; the apps proof; sealed-folder unpacking.
  The provider-store fixes (write budget, full key, standings cap) are one agent; partition mode, the first-seen
  log and the size estimate touch the DHT and go one at a time.
- **Merging.** Review each branch's diff (security-relevant code line by line) and check its commits carry no
  attribution before merging. When several branches are ready, merge them into a short-lived integration branch
  in a separate worktree, resolve conflicts there (the end of `statedb.SCHEMA`, CHANGELOG, `api.py`'s capability
  list, test fakes such as `tests/test_api.py`'s `FakeNode` are the usual ones), run the full suite and E2E on it,
  and merge it into `dev` only when green. Don't edit the main checkout while a suite runs there: its subprocess
  tests import the working tree.
- **Usage limits.** Agents have twice been stopped by a usage limit; their work stays in their worktrees. When the
  limit resets, resume each with a message rather than starting it again.
- **Can't be tested here:** Raspberry Pi and SD-card measurements, real LoRa, Windows, FAT32 with the private
  directory checks, the PyInstaller, .deb and Flatpak builds (CI runs those), the fuzz tests (hypothesis isn't in
  the venv). Note what each item leaves for them in the progress file rather than skipping silently.
