# 0.1.6 plan

The work for 0.1.6, alongside the feature items in [roadmap.md](roadmap.md). It merges three inputs from 2026-10-17:
- **Security fixes** for [0.1.5-audit.md](0.1.5-audit.md) (IDs `CONT-*`, `DHT-*`, `API-*`, `FEAT-*`, `NET-*`, `SUP-*`).
- **Maintainability work** from [maintainability-audit0.1.5.md](maintainability-audit0.1.5.md) (IDs `TS*`, `XC*`, `CT*`, `NW*`, `DH*`, `ND*`, `FT*`).
- **Performance work** from five read-only reviews (IDs `A*`–`E*`, `S*`).

Every item uses its source ID, so its full write-up can be found in that document. A design pass checked each
security and maintainability item against the tree at `5bd3075` (v0.1.5) and confirmed it. The line numbers
below are from that tree. Where the design pass corrected an audit, this plan says so.

**Rules for every item:**
- No wire changes: request paths (including feature paths such as keepers' `/name`), messages, CIDs, DAG bytes,
  chunk boundaries, provider and name records, and announce app_data stay byte-identical. 0.1.6 nodes must work
  with 0.1.5, 0.1.4 and 0.1.3 nodes.
- Server-side policy may tighten (cooldowns, pacing), but only in ways an honest 0.1.5 fetcher already handles.
- The local HTTP API stays compatible, status codes included. Where an item changes a default, it is listed
  under [Decisions](#decisions-needed-before-starting).
- Local state may change only with an automatic one-way upgrade. Downgrades need not work.
- rnfs is the core, and user-facing features belong in companion apps.
- Every security fix ports its PoC into `tests/security/test_<id>_*.py`.

**Numbers:** they come from the reviewers' NVMe machine and from simulated links (3 providers, 40 Mbit/s, 50 ms
RTT). Treat them as relative. Re-measure the items marked **(measure on Pi)** on an SD card before and after.

## Medium

### CONT-1. Bound the deny-list file-hash check (S, low)
- **Where:**
  - [node.py:799-813](rnfs/node.py#L799-L813) `_check_file` hashes the whole declared size.
  - Its callers: `_read` (`cat`, gateway GET and sniffing), the sealed `get`, `write_out` through `get`,
    `node_content.export_stream` and `import_archive`.
- **Change (assumes Q2 = ratio):**
  - New `walker.leaf_bytes(expect, get, stop_at)`. It walks file nodes only, each distinct node once, and adds
    `child.size` once per distinct raw child CID. It never reads raw blocks, and it stops early at `stop_at`.
  - `_check_file(expect, get)` now takes a getter, not a reader. In order:
    1. A raw digest, or a remembered hash, works as today.
    2. Otherwise compute `allowed = DENY_HASH_RATIO × leaf_bytes + DENY_HASH_SLACK`, with constants in
       `denylist.py` set to 16 and 64 MiB.
    3. If the declared size is over `allowed`, raise `Denied` (451): "can't be checked against this node's
       deny-list file hashes: it repeats its content more than 16×".
    4. Otherwise hash as now.
  - Use `Denied` rather than `TooLarge`, so `_refusing` collects what a refused import stored.
  - In `_read`, when `deny.hashes` is set, call `fetch.fetch_dag(...)` before the check, then pass `fetch.get`.
    This adds `check_disk`.
  - With the pre-check in place, `read_range` doesn't need a byte budget.
- **Docs:**
  - spec §8, deny-list bullet: the refusal rule and its 451.
  - spec §10, "Size lies" row.
  - spec §12, local defaults: the two constants.
  - design.md deny-list section.
- **Tests:** `test_cont1_deny_hash_amplification.py`:
  - The 6-block PoC through `cat`, a gateway `Range: bytes=0-0` request, `?format=archive` and import: each
    gives 451/`Denied` quickly, and a counting getter shows no raw block was read.
  - A 32 MiB repeated-chunk file, inside the slack, is still served.
  - An honest denied file still gives 451.
  - With no hash entries, nothing is walked.
- **Order:** land before or with E2 and API-5, which edit the same functions.
- **Done:** `5454d5d`

### API-1. Check `rnfs.toml` and existing subdirectories on POSIX (S–M, medium: new startup refusals)
- **Where:**
  - [config.py:274-282](rnfs/config.py#L274-L282); `winacl.secure_settings` does nothing off Windows.
  - [node.py:112-139](rnfs/node.py#L112-L139).
  - `cli.py:187` and `embedded.py:68` read the settings before the root is locked.
  - Also unchecked: `lxmf/`, and RNS's `config` when `reticulum_dir` is the rnfs dir.
- **Change:**
  - A new `fsutil.check_owned_fd(path, fd, info, what) -> warning | None`, shared with
    `network/identity._check_private`.
  - **`rnfs.toml`:**
    1. `os.open(O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC)`. `FileNotFoundError` means no settings, which replaces
       the `isfile` check; `ELOOP` means refuse.
    2. `fstat`: refuse anything that isn't a regular file, or whose `st_uid != geteuid()`.
    3. If `mode & 0o077`, `fchmod 0600` and add a warning.
    4. `tomllib.load` from that fd, capped at 1 MiB.
    5. The same check on `<root>/config` when `reticulum_dir` is the root.
  - **Subdirectories:** `_make_private_dirs(root)` opens each of `state`, `blocks`, `storage`, `names` and `lxmf`
    with `O_DIRECTORY|O_NOFOLLOW`, creating it 0700 if missing. A symlink, a non-directory or a foreign owner is
    refused with `RnfsError` naming `chown`. A loose one is `fchmod`ed to 0700 with a NOTICE. When the old mode had
    group or other write, one `lstat` pass warns about foreign-owned entries.
  - **Order at startup:** root, then settings, then subdirectories, then the lock. This applies in both
    `run_daemon` and `rnfs.Node`. `_make_private_dirs` takes the root, not a `Config`.
  - **Warnings without importing RNS** (this is also ND6):
    - `winacl.secure_settings` returns its reason instead of logging.
    - `Config.load` stores warnings on `config.warnings`, a plain attribute rather than a dataclass field, so
      rnfs.toml can't set it.
    - The daemon prints them with `cli.warn`; `rnfs.Node` logs them; the CLI client prints them; `rnfs.Client`
      raises `warnings.warn(RuntimeWarning)`.
  - **Windows:** also run `winacl.tighten(d, directory=True)` on existing subdirectories.
- **Docs:** spec §11. Existing subdirectories MUST be real directories owned by the user, and loose ones are made
  owner-only. A symlinked `rnfs.toml` is refused. CHANGELOG: dotfile setups that symlink `rnfs.toml` stop working.
- **Tests:**
  - `test_api1_settings_file.py`: 0666 becomes 0600 with a warning. A symlink or FIFO is refused without
    blocking. A foreign owner is refused (patch `geteuid`). A `python -I` subprocess shows that loading the client
    with a loose file doesn't import RNS.
  - `test_api1_subdirs.py`: 0777 becomes 0700. A symlink, a file or a foreign owner gives `RnfsError` before
    Reticulum starts.
- **Done:** `939ecae` (with ND6; `winacl.secure_settings` was replaced by `fsutil.check_owned_fd`, which returns the
  warning)

### CONT-2. Make `get` write-out immune to directory swaps (M, medium: rewrites the write-out loop)
- **Where:**
  - [walker.py:464-532](rnfs/content/walker.py#L464-L532): `os.mkdir(dest)` at :492, and children created by
    path at :511/:513.
  - The caller is `node.get` (`node.py:1052-1087`). Get jobs go through it too.
- **Change (POSIX, where `os.supports_dir_fd` and `O_DIRECTORY`/`O_NOFOLLOW` exist):**
  - **Partial root:**
    1. `mkdir`, then open it `O_DIRECTORY|O_NOFOLLOW`.
    2. Check its owner and `fchmod 0700`. Using mkdir then fchmod avoids the process-global umask and keeps
       setgid.
    3. Require the directory to be empty.
    4. Record its dev, ino and mode.
  - **Entries:**
    - Directories: `mkdir(name, dir_fd=parent)`, then reopen with `O_DIRECTORY|O_NOFOLLOW` and record dev/ino.
    - Files: `os.open(name, O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0o666, dir_fd=parent)`.
  - **Bounded fds:** the stack holds relative components plus dev/ino, not fds. A popped directory is reopened from
    the root fd one component at a time with `O_NOFOLLOW`. A mismatch raises
    `ValueError("output was changed while being written")`. Write order and warnings stay as they are.
  - **Finish:** `fchmod` the root back to its original mode. `get()` checks `lstat(partial)` against the recorded
    identity before `rename_new`.
- **Windows:**
  - Create the partial root with `winacl.make_private_dir`; its inherited protected DACL keeps others out.
  - After each `open("xb")`, check `fsutil.is_below(final_path(fd), real_root)`.
  - Before `rename_new`, a new `winacl.inherit_from_parent(path)` restores inheritance (Q13).
- **Unchanged:** single-file DAGs, which use `open("xb")` in a parent the user chose.
- **Docs:** spec §11 "Output from other nodes"; design.md (the `get` row and the partials paragraph).
- **Tests:** `test_cont2_write_out_swap.py`:
  - The deterministic swap PoC: a symlink fails, and nothing appears in the target. A swap to a real directory
    fails on dev/ino.
  - The root is 0700 during write-out and has its normal mode afterwards.
  - An entry planted before the chmod aborts the get.
  - 10k subdirectories don't exhaust fds.
  - Windows logic through a fake `winacl` backend (the `test_l7_windows_acl` style).
- **Done:** `04b3e2e` (the Windows path is tested only through the fake backend; on Windows a file created through
  a junction is left, empty, where the junction led)

### NET-1. Cool down responses cancelled before real progress (S, low)
- **Where:**
  - [server.py:1207-1238](rnfs/network/server.py#L1207-L1238) (`_concluded`, `_sent_any`); the cooldown check is
    at :902.
  - On RNS 1.5.6, any receiver cancel arrives as `REJECTED`. A link teardown arrives as `FAILED`.
- **Do NW2 step 1 first:** document which thread or lock owns each `Response` field. It's documentation only.
- **Change (assumes Q4):**
  - Replace `_sent_any` with `_made_progress(response, resource)`:
    - `sent = max(response.sent, resource.get_progress() × size)`;
    - return `sent >= NO_PROGRESS_FRACTION × size`, with `NO_PROGRESS_FRACTION = 1/4`;
    - if progress or the size can't be read, count it as progress, as today.
  - In `_concluded`'s `REJECTED` branch, call `self.cooldowns.add(link_id, identity)` when there was no
    progress. Reuse `Cooldowns` unchanged: flat `blocks_cooldown`, per link and per identity.
  - `FAILED` (link closed) deliberately gets no cooldown: in private mode an honest early-closing reader would cool
    its own identity down. Document that as a residual.
- **Honest 0.1.5 fetchers:**
  - They never call `Resource.cancel()`: stalls and early closes close the link.
  - The only honest RCL is RNS running out of retries on a lossy path. That peer then moves to another provider
    after `max_failures`.
- **Constraint for plan A1:** an early-closing reader must close the link, never call `Resource.cancel()`.
  Otherwise 0.1.6 would cool itself down at its peers.
- **Docs:** spec §3 Cooldown bullet, the threat table, and Limits.
- **Tests:**
  - `test_net1_cancelled_responses.py`:
    - a reject at 1% and at one window cools down the link and the identity;
    - one response is built per cooldown;
    - 25% and 50% get no cooldown;
    - a link close at 1% gets no cooldown;
    - `get_progress` raising gets no cooldown.
  - Move `reject()` from `test_l17` into `_server_helpers`. `test_l17` keeps passing; only its docstrings change.
- **Done:** `0ec517b` (NW2 step 1: `258afae`)

### DHT-1. Give keeper `/name` queries their own budget, and bound lookups (M, medium)
- **Where:**
  - [keepers.py:702-839](rnfs/features/keepers.py#L702-L839): `enough` at 746 and the
    `max(1.0, lookup.remaining())` deadline at 809.
  - [lookup.py:211-335](rnfs/dht/lookup.py#L211-L335): only "complete", "no node left" or the deadline ends a run.
- **Do FT2's extraction first,** as a behaviour-neutral commit: a `_KeeperQuery` class (`next_batch`, `ask`,
  `settled`) replacing the six closures. The behaviour changes then go in a separate commit.
- **Change (assumes Q10):**
  1. **`/name` budget:** each batch waits `max(lookup.remaining(), name_wait)` from when it starts, with
     `name_wait = path_timeout + links.ESTABLISH_GRACE + 5 × RNS.Link.ESTABLISHMENT_TIMEOUT_PER_HOP
     + links.DEADLINE_FACTOR × protocol.REQUEST_TIMEOUT_WITHOUT_RTT`. That is 87.5 s at the defaults.
  2. **Soft search budget:**
     - Stop the provider search when `enough()` holds, or when candidates exist and `lookup_timeout / 5` has passed.
     - If the batches don't settle and candidates run out with time left, resume `find_providers` and ask the new
       candidates.
     - Don't ask candidates as they arrive: reply order must not choose the keepers (spec §9).
  3. **Lookup bounds,** applied in `_iterate` as it stands (DH4's `_Run` is deferred):
     - a new `max_queries` parameter, defaulting to 8 × K (80) per run;
     - stop after 3 × window answers in a row (9) that don't shorten the bit length of the beta-th closest distance.
- **Docs:** spec §6 Termination (the cap and the no-progress stop); spec §9 Resolve (the soft budget, resume, and
  the separate `/name` wait).
- **Tests:**
  - `test_dht1_keeper_query_budget.py`:
    - slow Sybils that keep returning closer IDs, plus a keeper whose `/name` takes 3 s: the keeper's record is
      returned;
    - total time is bounded;
    - resume finds a later candidate.
  - `test_lookup.py`: the adversarial run ends at the cap or on no progress, and honest `find_closest` results on
    a simulated 2000-node network are unchanged.
- **Peers see:** fewer `/find` requests.
- **Done:** `73c8295` (FT2 extraction: `fbc4716`)

## A. Fetcher (phase 6)

### A1. `read_range` stops between windows (measure on Pi)
- **Problem:** [fetcher.py:86](rnfs/fetcher.py#L86) sets `WINDOW = 32` chunks. Each window has to finish before
  the next one is requested (around :605–629).
  - With 64 KiB chunks a window is only about 2 responses, so a third provider is never used and every link sits
    idle at each window boundary. FastCDC's smaller chunks make it worse.
  - Measured: a 48 MiB read took 8.97 s, against an ideal of 3.36 s, with links busy 51% of the time.
- **Change:**
  - Request the next window before the current one is handed back to the reader.
  - [fetcher.py:1069](rnfs/fetcher.py#L1069) currently drops verified blocks that are no longer `outstanding`.
    Store them instead.
  - If that is too invasive, a fallback: size the window as `2 × max_parallel × chunks per response`, not a
    fixed 32 (use NW5's `response_capacity`).
- **Constraint (NET-1):** a reader that gives up early closes its links. It must never call `Resource.cancel()`.
- **Remote load:** a reader that gives up early wastes up to one extra window.
- **Expected:** with A2, 8.97 s → 4.66 s (links 92% busy). `WINDOW = 128` alone gives 5.83 s.
- **Depends on:** TS3, XC7, NW1, NW5, CONT-1 (walker).
- **Tests:**
  - A multi-provider `read_range` keeps every provider busy across window boundaries.
  - An early-closing reader cancels cleanly, by closing its links.

### A2. Block writes delay the next request (measure on Pi)
- **Problem:** [fetcher.py:1070-1073](rnfs/fetcher.py#L1070-L1073) runs `_accept` → `session.put` →
  `BlockStore.put` (with fsync) for every block of a response. All of that happens on the fetch thread before
  `_assign` sends that provider its next request.
  - Measured: 63 ms per 16 × 64 KiB response on NVMe. SD cards and eMMC are typically 5–10× slower.
- **Change:**
  - Verify and count the response's blocks, call `_assign`, then write them through a pool such as
    `Session.writer()`.
  - Wait for every write before `ensure` returns, so durability and protection stay as they are.
  - `StorageFull` and `ValueError` (`BlockMismatch` after XC4) are raised slightly later, from that wait.
- **Depends on B:** if B removes the per-block fsync, most of this cost goes away. Re-measure after B before
  doing A2.
- **Expected (with today's fsync):**
  - 48 MiB `fetch_dag`: 5.21 → 4.43 s.
  - `read_range`: 8.97 → 6.37 s.
  - Tree of 8 KiB files: 1.35 → 0.75 s.
- **Remote load:** none.

### A3. Re-queueing scans the pending deque (phase 3)
- **Problem:** at [fetcher.py:845](rnfs/fetcher.py#L845), `cid not in pending` scans the whole deque. That
  happens for every CID of a BUSY, FAILED or STALLED result, and for every CID the responder's budget cut.
  - Measured: 20 ms per result at 16k pending (1 GiB); about 200 ms at 10 GiB, all on the fetch thread.
- **Change:** keep a `set` alongside `pending`, updated wherever `pending` is.
- **Tests:** existing fetcher tests. Add one for requeue ordering with a large pending queue.
- **Done:** `e54837a` (22.3 → 0.011 ms per BUSY result at 16k pending; 242 → 0.015 ms at 164k)

### A4. `fetch_dag` and `fetch_listing` wait for each tree level
- **Problem:** at [fetcher.py:527-539](rnfs/fetcher.py#L527-L539) and :553–563, the last request of each tree
  level leaves the other providers idle for up to one response.
  - Each level's leftovers also cost a separate small request. On a single LoRa provider that is a full extra
    request cycle plus the pacing wait.
  - The directory-tree simulation kept links only 30% busy.
- **Change:**
  - Queue a block's unseen children as soon as it is accepted, inside `_download`.
  - Count `max_entries` per block rather than per level. `_room` and `_reserve` already work per CID (in
    `_DagBudget` after NW1).
- **Remote load:** fewer, fuller requests.
- **Complexity:** medium (not prototyped). Keep the walk order the resume logic depends on.
- **Depends on:** as A1. CONT-1's `_read` now calls `fetch_dag` when deny hashes are set, so A4 speeds that up.

## B. Block write durability (Tier 1 #2): decision needed (Q1, phase 4)

### What IPFS (Kubo) does
- **Same storage design:** Kubo stores blocks in flatfs, one file per block written to a temp file then renamed,
  in sharded directories. That is the same design as rnfs's `BlockStore`. Kubo still calls flatfs "the most
  battle-tested and reliable datastore".
- **Kubo used to sync like rnfs:** until v0.33, flatfs ran with `sync: true`, fsyncing every block file and its
  directory. That is what rnfs does today.
- **Kubo now syncs at the durability point:** since v0.33, new repos get `sync: false`. The release notes say
  flushing on every block write is usually unnecessary, because Kubo flushes before and after critical
  operations like pinning. Users who want the old behaviour set `sync: true` and accept slower bulk adds.
- **Batching:** Kubo writes in batches of 128 nodes or 20 MiB (`Import.BatchMaxNodes`, `Import.BatchMaxSize`).
  A batch writes all its temp files, renames them, then syncs each touched directory once.
- **Concurrency:** flatfs caps concurrent batch writes at 16 (`maxConcurrentPuts`). Its reasons: macOS's
  default limit of 256 file descriptors, HDDs, and memory. rnfs's `WRITE_THREADS = 16` already matches, so
  **don't raise it to 64**: that would hit the macOS limit and hurt HDDs.
- **Corruption checks:** Kubo depends on content addressing for this. flatfs is "safe only for content-addressed
  data", and `Datastore.HashOnRead` is off by default.

### Libraries
- No Python library batches durable writes of many small files. `atomicwrites` and similar packages still do one
  fsync per file.
- The library route is an embedded key-value store, where one commit covers many blocks. Examples are LMDB
  (`lmdb`, a new native dependency) or SQLite (already shipped). This is Kubo's pebble/badger profiles.
- Taking that route means migrating the blockstore format and dealing with eviction and space reclaim. Kubo
  itself still defaults to flatfs. **Not recommended for 0.1.6.**

### Recommendation: copy Kubo's model instead of tuning thread counts
rnfs already has one durability point: `BlockStore.sync()`. It runs before every pin save
([storage.py:300](rnfs/content/storage.py#L300)) and cache save
([storage.py:323](rnfs/content/storage.py#L323)).

1. **No fsync on put:** `BlockStore.put` ([blockstore.py:73](rnfs/content/blockstore.py#L73)) writes the temp
   file and renames it, without the fsync, and adds the path to an unsynced set.
2. **Sync at the durability point:** `BlockStore.sync()` fsyncs every file in that set (at most 16 at a time,
   `fdatasync` where the OS has it), then the directory.
   - Optional, Linux only: a single `syncfs()` through ctypes could replace the per-file loop. Only adopt it if
     the measurement shows a clear win.
3. **Sync outside the lock:** `Session.writer()` close syncs its own blocks before returning, outside the storage
   lock. `_save_pins` runs `sync()` while holding the lock, so it should find nothing left to do.
   - The fetcher's blocks get synced at its `record_fetch` or pin step, as today.
4. **Keeping "no empty or short file under a CID name":** today's per-file fsync is what guarantees this
   ([specification.md](specification.md) §8).
   - Before the first unsynced write, create `blocks/.dirty` (one sync). Remove it after `sync()` completes.
   - At startup, if `.dirty` exists, hash-check the blocks modified since it was created (with a slack for
     clock steps). Delete any that don't match; they get fetched again. Use XC8's `blockstore.matches`.
   - Only an unclean shutdown pays for this check.
   - API-1 makes `blocks/` owner-only, so a recent block can't be planted by another local user in the meantime.
5. **Docs:**
   - specification.md §8: the pin and cache guarantee is unchanged. Add that a damaged recent block left by a
     power loss is found and removed at the next start.
   - Update design.md's storage section and `BlockStore`'s docstring to match.

### Decision gate before implementing
Benchmark a 256 MiB add, and a fetch of the same size, on NVMe and on a Pi 4 SD card in these variants:
- today's code;
- `fdatasync` only;
- deferred per-file fsync;
- deferred `syncfs`.

Go ahead with the deferred design only if it is at least about 1.5× faster on the SD card. If it isn't, fall
back to `fdatasync` (about +15%) and keep 16 threads.

**Harness done:** `1dcb7e0` (`tests/bench_block_writes.py`; run `python3 tests/bench_block_writes.py --dir
<dir on the SD card>`). **Gate pending:** the Pi SD-card run (maintainer). NVMe results, plain ext4, median
seconds (ratio to today):

| workload | today | fdatasync | deferred fsync | deferred syncfs |
|---|---|---|---|---|
| add, 256 MiB | 2.80 | 3.80 (noisy; min 1.27 vs 1.58) | 3.58 (0.78×) | 0.54 (5.2×) |
| fetch, 256 MiB | 14.5 | 25.9 (noisy; min 11.3 vs 11.4) | 4.15 (3.5×) | 0.65 (22×) |
| tree add, 4096 × 8 KiB | 2.64 | 2.91 | 3.78 (0.70×) | 0.57 (4.7×) |
| tree fetch | 24.9 | 23.3 | 3.52 (7.1×) | 0.27 (92×) |

On ecryptfs (an encrypted home) `syncfs()` returns without writing anything back, so the syncfs variant isn't
durable there; the harness warns about stacked filesystems. Deferred fsync is slower for adds (today's 16 writer
threads overlap their fsyncs with building the DAG) and much faster for fetches (today syncs each block on the
fetch thread). fdatasync alone gains nothing measurable on NVMe.

## D. Content and storage scaling (phase 5)

### D1. Shared folder re-imports a whole top-level directory
- **Problem:** at [shared_folder.py:226-243](rnfs/content/shared_folder.py#L226-L243), the signature covers
  the whole tree. One changed file reruns `build_open` on everything.
  - Measured: 0.44 s for 256 MiB / 5,000 files with one 4 KiB change. A 50 GB photo folder would re-hash 50 GB
    for each new photo.
- **Change:** a per-file cache of `(dev, ino, size, mtime_ns, exec bit)` → `(CID, size, content SHA-256)`. On a
  match where `is_complete(CID)` holds:
  - reuse the CID;
  - protect it in the session;
  - still run the deny check on the digest, passed explicitly through CT2's `BuildOptions.check`.
- **Trust model:** the same as today's signature. CONT-3's target guard runs before any cache reuse.
- **Storage:** start in memory. Persisting it (so a restart doesn't re-hash everything) needs a new statedb
  table with an upgrade migration. Build it as a `RowStore` (XC2), registered in the node's store list (XC5);
  TS2's digest test then shows the released steps were left alone.
- **Depends on:** CT2, XC5, XC2, CONT-3, TS2.
- **Tests:**
  - Changing one file re-hashes only that file.
  - A file renamed in place, or touched with the same size, is handled correctly.
  - A newly denied digest is still refused.
- **Done:** `60941cc` (in memory), `d677df6` (persisted: schema step 17, `shared_folder_files`). 1 GiB, 5000 files,
  one 4 KiB change: 1.20 → 0.10 s. A hit also requires no denied block in the file.

### D2. `dir set` / `dir rm` walk the whole tree to check depth
- **Problem:** at [edit.py:39](rnfs/content/edit.py#L39), `walker.height` decodes every node of the edited
  tree.
  - Measured: about 1 s per edit at 16 GiB (about 60 ms/GiB), so building a directory one entry at a time is
    O(n²).
- **Done:** `f109d25` (memo keyed by the checked expectation, in `walker.py`, at most 32 768; 16 GiB tree: an
  edit 0.9 s → 0.3 ms after the first)
- **Change:** memoise height by CID; content is immutable, so the memo never goes stale.
  - Keep it in `Storage` next to `_links`, or in a bounded LRU.
  - [walker.py:406](rnfs/content/walker.py#L406) consults it, so unchanged subtrees are O(1).

### D3. Storage walks complete DAGs again under the lock
- **Problem:** `_reach` ([storage.py:627](rnfs/content/storage.py#L627)), `_evict_to` (:796), `dag_blocks`
  (:832), `is_complete` (:921) and `dag_bytes` (:1081) all re-walk whole DAGs.
  - `_reach` costs about 1.1 µs per block while holding `_lock`: about 1.8 s per 100 GiB pinned, on every
    eviction pass, blocking every storage call.
  - `is_complete` on a 4 GiB DAG missing its first chunk takes 0.35 s, and eviction repeats it for every cached

- **Change:**
  - In `_reach`, take the union of the `_complete` frozenset for complete roots instead of walking.
  - Memoise the byte total of complete roots, which helps `dag_bytes` and `source_usage`.

  - Invalidate on delete, as `_complete` already is (through CT4's `_newly_incomplete`).
- **Depends on:** CT1, CT4, and CT6's injectable block-read hook if test_storage's patches of `_reach` and others

## E. Node, publisher and names (phase 7)

### E1. Gateway name resolves repeat network work (Tier 1 #4)
- **Problem:** in [names.py:797-843](rnfs/names.py#L797-L843), `resolve(max_age=GATEWAY_NAME_AGE)` (60 s)
  judges freshness by `record.heard`.
  - That time is capped at the announce's emission time plus 2 × `announce_interval`.
  - So once an owner has been offline for more than 12 h (the case keepers exist for), the record never counts
    as fresh.
  - Every gateway request then sends a path request, waits up to `path_timeout` (30 s), and runs
    `keepers.query` (a full `find_providers` lookup plus `/name` queries).
  - Simultaneous resolves of the same name aren't merged. A page with N assets under `/name/<n>/…` does all of
    that N times.
- **Change:**
  - Keep a per-name monotonic "last network refresh" time, and skip the refresh while it is within `max_age`.
    `contacts.py` does the same with `EXPAND_AGE`.
  - Merge in-flight refreshes: one caller runs `_refresh_name` (DH1) and the others wait on an `Event`, then do
    only the local final step. `persist` only affects that local step.
  - The refresh time is recorded even when nothing is found, which gives a short negative cache for names that
    don't resolve. It is **not** recorded when DHT-2 flags the record as a suspected replay.
  - CLI calls (`max_age=0`) never use the cache, but may join a refresh already running.
- **Depends on:** DH1 step 1, `_NameFloor`, the XC6 names waiter, DHT-1, DHT-2.
- **Remote load:** lower (fewer path requests, `/find` and `/name` calls).
- **Behaviour:** a name republished moments ago may show the older record on the gateway for up to 60 s.

### E2. Avoid re-checking whether a file is sealed, and repeating `pin ls` work
- **Sealed check:** `_info` / `_read` ([node.py:1098](rnfs/node.py#L1098), :1150) call `open_sealed` for every
  plain-file read. `read_file` (behind `/api/cat`) does it twice.
  - Change: keep a bounded LRU of file CIDs known not to be sealed (it never goes stale), and pass the
    `SealedFile` from `_info` on to `_read`.
  - Expected: a 64 KiB read goes from 1.3 to 0.5 ms.
  - **Depends on:** CONT-1, which edits `_read`.
- **`pin_ls`:** [node.py:1242](rnfs/node.py#L1242) re-reads and decodes each pin's root block, and for files
  also re-resolves the file and reads its first bytes.
  - Change: remember type, inside-name and sealed status per CID, bounded and pruned along with the pins.
  - Expected: 137–207 ms at 2000 pins drops to 3–4 ms on repeat calls.
- **Done:** `ed86aaa` (sealed check: 64 KiB read 0.32 → 0.19 ms here), `628ae2d` (`pin_ls`: 68 → 3.8 ms at 2000
  pins)

### E3. Publisher work after every add
- **Problem:**
  - `refresh()` → `_compute` ([publisher.py:414](rnfs/publisher.py#L414)) copies `storage.pins()`, including

  - Build the set of pending-withdrawal keys once per `refresh()`, and skip CIDs whose key isn't in it.
- **Done:** `19ae2bc` (first refresh, 10k CIDs × 300 nodes: 71 → 14.5 ms)

## Not doing in 0.1.6

| Item | Why not |
|---|---|
| **FEAT-3 LXMF stamps** | Announcing a `stamp_cost` changes announce app_data, and enforcing it refuses senders that haven't heard the new announce. For 0.1.7: an opt-in `lxmf_stamp_cost` (default 0, so the announce is byte-identical), with `enforce_stamps` off and a valid stamp used as a priority for strangers rather than a gate. |
| **DHT-6 ID grinding** | Raising the cost of IDs changes how they are derived (a wire and design change). A later local mitigation: keep one of alpha's slots for the closest unqueried senior node. |
| **NET-4**, if phase 6 runs long | It depends on the A-series fetcher changes. Otherwise 0.1.7. |
| **CONT-4 CID denies from remembered hashes** | M-sized, because it needs a change trigger in `_apply_deny`. Chunks must never be auto-denied. |
| **API-4 dropping the fallback** | It would break newer clients against deb-installed 0.1.4 daemons. Gate it on version in 0.1.6 (above) and drop it in 0.1.7. |
| **SUP-6 signing (Authenticode, apt, Flatpak) and an SBOM** | Needs keys and infrastructure. |
| **ND1, FT1 package split, rest of DH1, DH5 legacy moves** | Large, and in the files with the most churn and open security fixes. 0.1.7, each in its own release. |
| **NW2 lock and NW3 split** | `/blocks` is mid-fix for NET-1/2. Step 1 (docs) is in 0.1.6. |
| **XC1 feature boundary** | Decides how easily features move to companion apps. It also covers moving cli.py and the feature CLIs onto `ApiConnection`, and deduplicating the add options. 0.1.7. |
| **XC2 for lxmf, follow and keepers; XC6 waits in server and links** | Wait for FEAT-*, DHT-3, DHT-1 and NET-1 to settle. |
| **DH3 `_Round`, DH4 `_Run`, NW1 `_Providers`/`_Download`** | No 0.1.6 item needs them, and DH4 must wait for DHT-1's bounds to settle. |
| **CT5 headers module, XC8 `fmt.py`** | Little gain, and `fmt.py` changes CLI output. |
| **XC8 token buckets** | lxmf's two-level buckets don't fit `mesh.TokenBucket`. |
| **TS8 composite install action, TS9 regrouping, rest of ruff B** | Large renames or rewrites while the fetcher work is in progress. |
| Hash each block once (trusted put path) | About 10% on add and fetch, but a "skip verification" path is a security boundary that must never reach unverified callers. Needs its own review. |
| `dag._decode` canonical check without re-encoding | About 40% of decode time, but it changes validation code: the accepted set of encodings must stay exactly the same. Needs fuzzing against the current check first. |
| Gateway resolves `index.html` directly | A missing entry and an unreachable block both raise `NotFound` today, so it needs a new error type. Only helps directories over 128 KiB. |
| Pacing sends about one RTT earlier on slow links | Changes timing seen by remote peers (handler threads held longer). |
| Even split of the final batch across providers | Sends more requests to remote peers, for a small gain at the end of a fetch. |
| Raise `WRITE_THREADS` to 64 | See B: flatfs keeps 16 for macOS's file-descriptor limit and HDDs. |
| Merge the gateway's 3 fetch sessions; `next_due` SHA-256; `walker.step` building `Expect`s; `BlockStore.delete` stat | Negligible. |

Already measured as fine, so not worth revisiting:
- DHT lookups and the routing table's `closest`;
- statedb (WAL, primary-key access, `executemany`);
- denylist frozensets;
- CLI startup (about 50 ms, and RNS isn't imported);
- logging cost when the level is off;
- API and gateway streaming;
- the chunkers;
- sealing.
